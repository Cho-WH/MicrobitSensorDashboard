# Bluetooth 설치·연결 개발 설계

> **무선 설치 1안 확정(2026-10-27): 공통 런타임 안의 부분 교체.** BMP280 8,320B의 전송 5.3984초 실측을 근거로 제품 통합을 진행한다. **이번 제품 구현은 부분 교체만 포함하며, 런타임이 다르면 USB 설치를 안내한다.** 전체 교체 C는 핵심 실험 결과만 보존하고 시험 도구·전용 파일은 제거했다. 제품 경로에는 연결하지 않는다. USB 기본 설치·최초 준비·복구 경로는 유지한다.
> **확정일: 2026-10-27.** 부분·전체 교체의 연결 복구는 **즉시 시도 → 실패 후 2초·4초·8초 대기, 총 4회**로 한다. 소진하면 자동 작업을 멈추고 **보드 리셋 후 다시 시도**하도록 안내한다. 재연결 과정에서 펌웨어 전송이나 측정 시작을 반복하지 않는다.
> **현재 구현:** 정식 앱의 기존 프로그램 단계에 USB↔무선 전환, 부분 설치, 연결 복구·리셋/USB 안내, 같은 보드의 측정 연결 인계를 구현했다. 등록 센서 5종의 기본 배포 파일은 공통 B 런타임으로 교체했다. 앱 통합은 모의 장치와 브라우저에서 확인했으며 정식 화면의 실물 인수는 남아 있다. 개발 시험본 B/C의 실물 결과와 구분한다. 서비스 조회 2초 제한에서 오류 발생 후 실물 자동 복구는 별도 재확인이 필요하다.

## 1. 목표와 현재 구현

USB를 기본 설치 방법으로 유지하면서, 준비된 micro:bit V2의 프로그램을 앱 안에서 Bluetooth로 교체하고 같은 보드의 측정 연결로 이어간다. 최초 준비는 선택 센서의 전체 HEX 하나를 USB로 설치한다. OS 본딩·PIN·기기 등록 삭제·외부 모바일 앱은 정상 사용 절차에 넣지 않는다. 브라우저 장치 선택과 권한 허용은 필요하다.

| 구분 | 개발 기준 | 구현 상태 |
|---|---|---|
| 무선 설치 1안(확정) | 공통 런타임 안의 부분 교체. 런타임 변경·비호환은 USB | 정식 앱 통합·모의 확인, 실물 인수 대기 |
| 전체 전송 비교 경로 | 비본딩 전체 애플리케이션 교체. SoftDevice·부트로더 제외 | 시험본 C 온도/밝기 4회 확인. 이번 제품 구현 범위 제외 |
| 공통 연결 복구 | §5의 2·4·8초 정책과 제한된 연결·조회 재시도 | 정식 앱의 공통 정책 모듈 사용. 실물 근거는 §8.4 |
| 사용자 복구 | 자동 복구 소진 → 물리 리셋 안내 → 사용자가 다시 시도 | UI·수동 재진입 구현, 전송 완료 근거 보존 모의 확인 |
| 배포 펌웨어 | 등록 목록·버전·해시를 검증 후 갱신 | 5종 정식 V1 (`sensor-lab-*`). 공통 B `pairing_mode: 1`; 이전 `*-uart` 설치 파일은 제거하고 저장 자료 호환용 stale 메타데이터만 보존. 새 표시·실물 수신은 확인 대기. 이전 자기장 v5의 보정 완료 유지·재연결은 사용자 확인 완료(2026-10-27) |

### 1.1. 선택 근거와 적용 원칙

- BMP280 부분 교체는 **8,320바이트, 5,398.4ms, 블록 재전송 0회**였다. `flash-start`부터 `flash-finish-requested`까지이며 프로토콜 확인 응답은 포함하고 재부팅·연결 해제 대기·재연결은 제외한다. 프로그램 식별·새 측정값 3개 수신과 온도 복귀까지 성공했다. 당시 시험 도구와 집계는 Git 커밋 `e0d4f41`에서 확인할 수 있다.
- 비교한 전체 C는 온도·밝기 **188,640–188,816바이트, 전송 24.7–26.9초**다. 부분 BMP280의 전송 구간이 약 4.6–5배 짧았다. 서로 다른 프로그램의 비교이며 BMP280 전체 교체는 실측하지 않았다. 이번 부분 측정은 1회이므로 전체 설치 시간·평균 성능·안정성 우위를 단정하지 않는다.
- 용량 차이의 주원인은 공통 런타임이다. 전체 C는 런타임과 프로그램을 함께 보내고 부분 B는 호환 런타임을 유지한다. 두 경로 모두 SoftDevice·부트로더는 덮어쓰지 않는다.
- 학생 화면에는 Bluetooth 설치 경로를 제공하고 부분/전체 방식을 선택하게 하지 않는다. 호환성이 확인된 등록 프로그램에 부분 교체를 사용한다. 런타임 변경·비호환은 USB로 안내한다. 외부 펌웨어가 DFU를 지원하더라도 이번 제품에서는 전체 교체를 제공하지 않으며 자동 전환도 하지 않는다.
- 안정성 근거는 기존 부분 32회·전체 4회와 이번 BMP280 왕복을 구분한다. 서비스 조회 2초 정책에서의 오류 복구, 전송 중단 복구, 다중 보드·지원 환경 검증과 정식 화면의 실물 인수는 남은 작업이다.

## 2. 지원 범위와 진입 조건

- 첫 지원 기준은 V2·Windows Chrome에서 확인한 경로다. 다른 보드·OS·브라우저의 공개 지원은 별도 실물 확인 후 표시한다. Web Bluetooth에는 HTTPS 또는 localhost와 사용자 동작에서의 장치 선택이 필요하다.
- 같은 브라우저 장치 객체를 재사용하고 재연결 후 모델·모드·런타임·프로그램을 다시 조회한다. 주변 첫 장치를 임의로 고르거나 브라우저 ID를 네이티브 MAC 주소처럼 취급하지 않는다. C의 같은 ID 재사용은 한 대만 켠 시험 조건의 근거다. 여러 보드에서의 동일성 확인은 제품 통합 전 검증한다.
- 부분 전송은 지원 V2, 서비스·모드, 등록된 파일의 해시, 런타임 식별값, 프로그램 시작 주소와 허용 영역을 모두 확인한 뒤 허용한다. 이름·마지막 설치 기록만으로 호환을 판정하지 않는다.
- 현재 USB 번들의 공식 microbit-connection 1.0.0과 조사한 최신 소스를 구분한다. 공식 라이브러리의 공개 웹 Bluetooth 전송 지원을 가정하거나 USB 번들의 export만 늘려 해결하지 않는다. 검증된 개발 어댑터를 이식한다.
- iOS의 Bluefy 측정 안내는 설치 지원 근거가 아니다. API 존재·기존 USB/측정 검증과 Bluetooth 설치 검증을 구분한다. 기존 브라우저의 저장 자료는 실험 파일로 옮긴다.

## 3. 설치 화면과 사용자 흐름

1. 기존 준비 흐름의 프로그램 단계는 USB 설치가 기본이다. “센서 실험실의 다른 프로그램이 설치돼 있나요? USB 없이 프로그램을 바꿀 수 있어요.” 아래 **무선으로 설치하기** 글자 링크로 전환한다. 같은 단계·화면에서 설치 방식만 바꾸고 **USB로 설치하기** 링크로 되돌린다. 무선 모드에는 전원·거리·보드 선택·최초 USB 설치 안내를 표시한다. 별도 창이나 준비 단계를 만들지 않으며 지원 불가 환경에는 보드 조작 전에 대안을 표시한다.
2. 기록 중이거나 저장이 끝나지 않았으면 설치를 시작하지 않는다. 기존 측정 작업을 정리하고 연결 제어권을 설치 어댑터로 넘긴다. 사용자 자료·실험·센서 선택은 유지한다.
3. 대상 파일 검사 → 보드 연결·호환 확인 → 필요한 모드 전환 → 연결·서비스 준비 → 부분 전송 → 실행 모드·프로그램 확인 순서로 진행한다. 런타임 불일치가 확인되면 전송 전에 멈추고 **“이 보드는 USB로 프로그램을 먼저 설치해야 해요. USB 케이블을 연결해 설치해 주세요.”**와 **[USB로 설치]**를 제공한다. 조회 시간 초과·연결 오류는 런타임 불일치로 간주하지 않고 §5 재시도 정책을 따른다. 서비스 조회 성공만으로 설치 성공을 표시하지 않는다.
4. 학생 안내는 설치 전·진행·완료로 나누고, 내부 호환 확인·모드 전환·서비스 조회는 개별 단계로 표시하지 않는다. 진행 중에는 **“프로그램을 설치하고 있어요.”**와 전원을 유지하고 기다리는 행동을 안내한다. 전송이 끝나면 전송률을 숨기고 **“설치를 마무리하고 있어요.”**로 바꿔 §5의 자동 복구와 설치 확인을 기다린다. 대기 중에도 취소를 제공한다. 내부 UUID·GATT·재시도 코드나 고정 완료 시간은 학생 화면에 노출하지 않는다.
5. 자동 연결 복구를 모두 소진하면 다음 안내를 표시한다.

   > **보드에 다시 연결하지 못했어요. micro:bit 뒤쪽의 리셋 버튼을 한 번 누른 뒤 ‘다시 시도’를 눌러 주세요.**

   카드의 제목과 행동 안내를 분리하고, 기존 주황 강조색과 뒷면 버튼 위치 그림을 사용한다. 동작은 **[다시 시도]**, 보조 **[USB로 설치하기]**다. 복구 중에는 기설치 확인과 다음 단계 버튼을 숨긴다. USB가 필수인 경우에는 USB 연결 그림과 **[USB로 설치하기]**를 주 행동으로 표시한다. 여기서 리셋은 뒤쪽 버튼의 짧은 누름이며 A+B를 누른 채 리셋하거나 OS 기기 등록을 삭제하는 절차가 아니다. 앱이 리셋 명령을 자동 반복하지 않는다.
6. **다시 시도**는 기존 연결·미완료 요청을 정리하고 동일 보드의 연결·상태 조회부터 새 복구 주기로 시작한다. 브라우저가 재선택을 요구하면 이 사용자 클릭 안에서 선택창을 연다. 전송 완료 근거는 유지한다. 대상 프로그램이 확인되면 전송을 다시 하지 않고 설치 확인·측정 연결로 이어간다. 전송 전 실패였다면 호환·모드를 재확인해 요청된 설치를 진행한다. 전송 도중 중단됐거나 상태를 신뢰할 수 없으면 검사 생략 없이 USB 복구로 안내한다.
7. 사용자 취소는 취소로 끝낸다. 권한 거부에는 권한/장치 선택을, 파일 손상·비호환에는 파일/USB 경로를 안내한다. 이들을 모두 리셋 안내로 묶지 않는다. 리셋 뒤에도 같은 자동 복구 주기가 실패하면 USB 대안을 유지하고 사용자의 새 동작 없이 반복하지 않는다.
8. 무선 설치 완료는 기존 초록 강조색과 **“설치가 끝났어요.”**로 안내하고 재설치는 보조 행동으로 둔다. 설치 후 이동 버튼은 USB와 동일한 **[확인했어요 · 다음 →]**이며, 이후 연결·수신·보정 화면과 버튼도 기존 USB 흐름을 공통으로 사용한다. **[micro:bit 연결]**을 누르면 USB 설치 뒤에는 Bluetooth 장치를 선택하고, 무선 설치 뒤에는 설치한 보드의 연결을 내부에서 측정 모듈로 넘긴다. 인계 전에는 과거 측정 장치의 재연결·다른 장치 선택 버튼을 표시하지 않는다. 공통 안내는 선택창이 열리는 경우에만 장치를 선택하도록 표현한다. 사용자가 연결·수신 확인 또는 측정을 시작할 때 센서별 새 유효값·보정 절차를 확인한다. 설치 완료만으로 보정 완료·기록 시작·이전 기록 재개를 만들지 않는다.

## 4. M6 구현 순서와 완료 기준

**M6-1 구현(2026-10-28):** USB 설치 단계의 보조 버튼 **설치에 문제가 있나요?**가 공통 도움말 대화상자를 연다. 케이블·포트 확인, 다른 탭의 연결 해제, MICROBIT 드라이브에 HEX 파일을 복사하는 대안을 제공한다. 파일은 현재 선택 센서의 설치 허용 목록에서 고르고 직접 USB 설치와 같은 해시 검증을 거친다. 직접 설치 미지원 안내는 본문에 유지한다. 다운로드는 설치·준비 완료 상태를 변경하지 않으며 실제 복사 후 기존 기설치 확인·Bluetooth 새 수신 절차로 이어간다. 기록·저장·연결 가드는 기존 설치와 공유한다.

관련 단위 11개·타입 검사와 브라우저 10개가 통과했다. USB 미지원 환경의 파일 받기, 손상 파일 거부·재시도, 센서별 파일 일치, 설치 상태 보존, 작은 화면 닫기·초점 복귀와 기존 USB/무선 설치 경로를 확인했다. 내려받은 파일을 보드에 복사하는 실물 확인은 남아 있다.

|---|---|---|
| M6-1 | USB 도움말·고정 HEX 받기 구현 | 기존 펌웨어 목록 재사용, 다운로드와 실제 설치 성공 구분. 자동 검증 완료·파일 복사 실물 확인 남음 |
| M6-2 · 연결 통합 | §5 정책과 §3 리셋 안내를 앱의 설치·측정 연결에 연결 | 재시도 범위·횟수·취소·상태 조회·수동 재진입 구현, 실패 뒤 무단 재전송 없음 |
| M6-2 · 프로그램 등록 | 공통 계열·센서별 파일/codec/버전/해시 검증 | 배포용 USB HEX와 무선 파일의 일치, 런타임 비호환 쓰기 0회 |
| M6-2 · 인수 | 저장 가드, 새 수신, 리셋/USB 복구, 공개 환경 검증 | §8의 미확인 항목을 실제 지원 범위에 맞춰 확인 |

연결 통합·5종 프로그램 등록은 구현했다. 다음 작업은 정식 화면의 실물 인수다. 기본 정책을 정하기 위한 동일 조건의 무제한 반복 시험은 끝냈다. 전체 C의 제품 채택과 일반 센서 확장은 이 결정으로 자동 확정하지 않는다.

## 5. 연결·재시도·실패 처리 계약

### 5.1. 공통 재연결 원칙

| 항목 | 확정 규칙 |
|---|---|
| 연결 유지 | 진단↔UART 역할 전환·측정 중단·성공한 시험 종료만으로 유효 GATT 연결을 끊지 않는다. 명시적 해제·실패·취소와 재부팅 시 정리한다. |
| 재부팅 대기 | 재단 방식에 따라 실제 해제 이벤트를 최대 10초 기다린다. 이벤트가 오면 즉시 다음 단계로 간다. 명령 쓰기 완료 후에도 이벤트가 없으면 기존 연결을 정리하고 새로 조회한다. 이벤트 미수신 사실을 기록한다. |
| 자동 재시도 | 첫 시도는 즉시, 일시적 실패 뒤 2초→4초→8초 대기, 총 4회. 성공하면 남은 대기는 생략한다. 매번 서비스·특성을 새로 얻는다. |
| 조회 제한 | 서비스·특성 조회는 호출마다 2초. B/C 진단, C DFU 사전 준비, B/C UART 탐색에 적용한다. GATT 연결·응답·재부팅 대기 제한과 전송 라이브러리 내부 동작은 유지한다. 백그라운드 타이머 지연으로 실제 종료는 2초를 넘을 수 있다. |
| 대상 작업 | 같은 보드의 GATT 연결, 필수 서비스·특성 조회, 상태·식별 읽기, 측정 시작 전 알림 준비. 부분 교체의 모드 전환 전후와 C의 DFU 준비/설치 후 연결에 적용한다. |
| 일시적 실패 | 연결 단절, 연결/조회 시간 초과, 모드 전환 중 서비스 미준비. `NotFoundError`를 장치 선택 취소와 혼동하지 않고 연결 준비 범위에서만 다룬다. |
| 즉시 중단 | 권한 거부·사용자 취소·다른 보드·런타임/프로그램 불일치·파일 검증 실패·잘못된 프로토콜 응답. 리셋으로 검사를 우회하지 않는다. |
| 반복 금지 | 모드/DFU 진입 명령, 펌웨어 전송, Execute, 측정 시작을 이 재시도 루프에 넣지 않는다. 부분 프로토콜의 명시적 블록 NACK 처리는 별개다. |
| 소진 | 연결 복구 필요 상태로 전환해 §3의 리셋 안내를 표시한다. 자동 전송 재개·자동 리셋·다른 장치 선택은 하지 않는다. |
| 시간 표현 | 14초는 설정 대기의 합계다. 연결·서비스 조회 시간이 추가되므로 전체 복구 완료 시간으로 표시하지 않는다. 부분 실물 복구는 16.1–18.6초였다. |
| 측정 수명 | 측정 시작 뒤 수신 단절·이전 기록 자동 재개는 Session/Transport의 별도 계약을 따른다. 이 정책으로 측정 시작을 재전송하지 않는다. |

기존 단계별 응답 제한과 취소 검사를 유지한다. 종료한 시도의 늦은 응답이 새 시도를 성공시키거나 새 연결을 끊지 않게 작업 식별자와 연결 소유권을 확인한다. 재시도 대기 전후에 취소를 확인하며 동시 connect·진단·설치 요청은 허용하지 않는다. 모든 단절 이벤트에 무조건 재연결하는 전역 루프는 만들지 않는다.

### 5.2. 상태와 재진입

| 상태 | 다음 동작·완료 기준 | 실패 시 처리 |
|---|---|---|
| 준비·호환 확인 | 고정 파일 검증, 같은 보드·런타임·영역 확인 | 비호환/손상은 USB 또는 파일 복구 |
| 모드 전환 | 명령 한 번 → 해제 대기 → 연결 준비 | 명령 거부는 중단, 연결 실패는 자동 복구 |
| 연결 준비 | 연결·필수 서비스/특성·현재 모드 조회 | 일시적 오류만 4회까지, 소진하면 리셋 안내 |
| 전송 | 기존 전송 엔진의 무결성·완료 조건 수행 | 전송 미완료 보존, 무조건 재전송하지 않음 |
| 설치 확인 | 같은 보드·일반 모드·목표 프로그램 확인 | 연결 오류는 자동 복구, 식별 불일치는 중단 |
| 측정 준비 | 연결 인계·알림 준비 후 센서별 새 수신 확인 | 시작 전 연결 오류만 복구, 시작 후 실패는 별도 측정 계약 |
| 리셋 안내 | 사용자가 물리 리셋 후 다시 시도 | 새 연결·조회부터 재검증, 검증 불가/반복 실패는 USB |
| 취소·실패 종료 | 요청·알림·연결 정리, 근거와 오류 보존 | 후속 명령 자동 실행 없음 |

전송 완료, 장치 프로그램 확인, 새 수신은 별도 사실로 유지한다. 100% 표시·쓰기 완료·연결 해제만으로 설치 성공을 만들지 않는다. 이미 확보한 전송 완료 근거를 후속 연결 오류로 지우지 않는다. 반대로 최종 전송 응답을 못 받았다면 같은 프로그램 헤더·측정값을 읽어도 그 전송을 성공으로 소급 확정하지 않는다.

## 6. 개발 로그와 시험 도구

설치 어댑터의 이벤트 콜백으로 정책 버전·단계·시도 번호·경과 시간·원래 오류·대기·전송 완료·프로그램 확인을 관찰할 수 있다. 정식 앱은 원본 로그를 DB에 누적 저장하지 않는다. `connection-backoff-2-4-8-discovery-2s-v2`가 현재 정책이다. 학생 화면에는 연결/재연결/리셋 안내만 보여 준다.

무선 시험 페이지·CLI·왕복 실행기·전체 교체 C 전용 코드와 파일은 2026-10-27에 제거했다. 재현이 필요하면 Git 커밋 `e0d4f41`의 `dev/bluetooth-install/`을 확인한다. 원본 실기기 로그는 `.local/logs/bluetooth/`에 로컬 보존하며 Git에 추가하지 않는다. 이 경로는 테스트 실행 결과 폴더와 분리해 자동 정리로 지워지지 않도록 한다.

## 8. 개발·검증 계획

정책 구현·기본 실물 복구 검증은 완료했다. 제품 통합에서는 연결 정책을 바꾸지 않고 다음 경계를 확인한다.

- 관련 자동 검사: 첫 성공, 네 번째 성공·소진, 서비스 부재와 권한 거부 구분, 대기 중 취소, 늦은 응답, 보드/프로그램 불일치, 전송/측정 시작 비반복.
- 리셋 안내: 네 번 실패한 상태에서 안내 노출, 사용자의 물리 리셋·다시 시도, 새 조회, 전송 완료 근거 보존, 반복 실패/손상 시 USB 안내. 이 사용자 흐름은 아직 실물 미검증이다.
- 설치 복구: 첫·중간·마지막 전송의 단절/전원 차단, 긴 프로그램→짧은 프로그램, 파일 경계·예약 영역, USB 복구. 중단 시 이전 프로그램 보존은 보장하지 않는다.
- 앱 통합: 미저장 자료·분석 초안 보존, 기록 가드, 센서별 보정·명령·codec, 새 수신 확인, 자동 기록 재개 없음.
- 공개 지원: 다른 보드·복수 보드 식별·다른 OS/브라우저, 외장 센서의 배선·측정 정확도는 지원 범위에 맞춰 확인한다. 이번 보드 한 대 결과를 모든 환경의 보장으로 확대하지 않는다.

2026-10-27 자기장 v5는 사용자가 보정 완료 기억·재연결 후 수신 확인이 의도대로 작동함을 실기기에서 확인했다. 정식 V1의 LED 표시·센서 정확도·모든 기기와 브라우저를 검증한 결과는 아니다.

정식 앱 통합의 모의 검사는 비호환 쓰기 차단, 취소, 전송 중단 시 USB 안내, 전송 완료 뒤 재연결 실패·수동 재시도 시 재전송 금지, 같은 연결의 측정 인계, 구버전 자료 호환을 확인한다. 브라우저 검사는 같은 단계의 모드 전환·모바일 USB 안내·측정 연결 흐름을 확인한다. 정식 V1의 5종 설치·기본 수신은 위 환경에서 확인했으며, 물리 리셋 복구·전송 중단·보정 완료·LED 동작·지원 환경별 실물 인수는 남아 있다. 과거 1.2초 재시도, 고정 부팅 대기, 자체 DFU 속도 비교, 본딩형 진입 실패는 로컬 이력이며 현재 구현 지침으로 사용하지 않는다.

같은 정식 V1 확인 중 BMP280 수동 연결 해제 후 ‘이전 장치에 다시 연결’이 연결 중에 머물렀고, 취소 후에도 대기가 끝나지 않아 새로고침했다. 이후 선택창에서 기기가 사라졌으며 사용자는 보드의 측정 파형 표시가 유지됨을 확인했다. USB 재설치로 복구했다. 일반 연결 경로의 GATT 연결·서비스 조회·알림 준비에 제한 시간이 없고 취소가 진행 중 연결의 반환을 기다리는 코드 경로는 확인했으나, 실제 멈춘 단계와 보드·OS·브라우저 중 원인은 원시 통신 로그가 없어 확정하지 않는다. 이 사례는 무선 설치 성공과 별도의 미해결 재연결 문제로 관리한다.

위 정식 V1 실물 결과는 이름 스크롤 전에 아이콘을 지우는 표시 수정 이전 빌드 기준이다. 사용자 요청으로 버전 번호는 V1을 유지해 교체했으며, 수정 후 표시의 실물 가독성은 재확인하지 않았다.

**복구 시간 분석(같은 로그 6건):** 두 번째 시도의 GATT connect는 7–27ms에 완료됐지만 장치 정보 서비스(0x180A) 조회가 미완료인 채 `diagnostics.js`의 6,000ms 제한에 걸렸다. `trace-timeout` → `cleanup: timeout` → 앱의 명시적 disconnect 순서가 모두 확인됐다. 즉 두 번째 실패는 보드의 자발적 단절로 판정하지 않는다. 모든 탭 상태가 hidden이었고 타이머는 실제 6.956–6.976초 뒤 실행됐다. 약 1초 추가 지연과 4초 대기의 약 5초 실행은 [Chrome의 백그라운드 타이머 일괄 실행](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)과 일치한다. 최초 서비스 조회 Promise는 앱 정리 뒤에도 남아 호출 후 약 9.98–10.01초에 거부됐다. 서비스 조회가 멎는 근본 원인이 보드·Windows·Chrome 중 어디인지는 이 로그만으로 확정하지 않는다. 후속 결정으로 서비스·특성 조회 제한만 2초로 줄였다. 당시 B의 성공한 서비스 조회 544건은 모두 2초 이내(최대 약 1.55초)였다. 위 복구 시간은 변경 전 6초 제한의 기록이며, 2초 제한에서의 실물 복구 성공 여부·시간은 재확인이 필요하다.

## 9. 공통 런타임 구축과 확장 설계

### 9.1. 호환성과 확장 경계

[펌웨어 빌드·배포의 공통 런타임 기준](../dev/firmware/README.md#공통-런타임과-검증-경계)을 따른다. 부분 교체는 검증된 프로그램 영역 전체를 설치하며 실행 중 모듈을 덧붙이는 기능이 아니다. 설치 어댑터는 보드·런타임·주소·파일을 쓰기 전에 검사한다. 비호환 또는 손상된 헤더는 USB 복구로 안내한다. 런타임이 같아도 센서 채널·단위·기존 기록과 호환된다는 뜻은 아니다.

### 9.2. 빌드·배포 계약

소스·도구·네이티브 입력·산출물 해시와 버전 고정은 [빌드·배포 문서](../dev/firmware/README.md)가 소유한다. 앱은 생성된 현재 목록만 설치 대상으로 해석하며 저장 자료의 버전·해시를 바꾸지 않는다. 임시 개발 버전은 호환 목록에 누적하지 않는다. 프로그램 동작·통신은 [공통 동작 규약](sensor-program-contract.md)을 따른다.

### 9.3. 외장·복합 후보의 현재 계약

- **BMP280:** 명령·단위·결측은 [공통 동작 규약](sensor-program-contract.md#4-센서별-계약)을 따른다. [로컬 드라이버](../firmware/drivers/bmp280.ts)는 Bosch 보정식·온도/압력 6바이트 일괄 읽기를 사용한다. 원본 BME280_2 확장 커밋 `141a8f57653535b082926777c3ef79c8b7269964`와 MIT 출처를 보존하고 과거 자료는 재계산하지 않는다. 기본 배포는 `sensor-lab-bmp280` 정식 V1이며 이전 `bmp280-uart`의 자료는 기존 ID·버전으로 해석한다. [수치 검사](../tests/unit/external-sensor-firmware.test.mjs)는 센서 정확도 검증을 대신하지 않는다.
- **아날로그 기반:** P0/P1/P2 순차 읽기, 3열 ADC 원시값 0–1023, 명목 100ms, `start`/`stop`. 0·1023은 결측이 아니다. 물리량 변환·핀·범위·보정은 개별 센서 정의에서 정한다. 현재 실물 근거는 센서 미연결 수신이며 기준 전압/실제 센서 검증은 별도다.
- **temperature-light:** 다중 소스·기존 API 사용 시 런타임 동일성을 검사하는 결합 예제다. 빌드됐다는 이유로 앱 센서로 자동 등록하지 않는다.

## 10. 종료된 전체 교체 실험

2026-10-27 비본딩 전체 교체 C는 온도·밝기 2왕복·4회, 전송 구간 약 24.7–26.9초를 확인했다. 제품은 공통 런타임 안의 부분 교체를 채택했다. 전체 교체 시험 도구·파일·전용 캐시·라이브러리는 제거했으며 구현과 상세 절차는 Git 커밋 `e0d4f41`에 남아 있다. 이 결과를 현재 정식 V1의 실물 인수로 간주하지 않는다.
