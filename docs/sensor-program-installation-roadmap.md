# 센서 프로그램 설치 개선 — 공통 런타임과 Bluetooth 부분 교체

> 결정: 2026-10-26 **USB 기본·공통 런타임 안의 Bluetooth 부분 교체**를 채택했다. 앱의 모든 센서 프로그램을 같은 런타임 계열로 빌드하고, 무선으로 센서별 실행 코드 전체를 교체한다. 최초 준비·런타임 변경·비호환·복구는 USB로 처리한다. 본딩을 요구하는 전체 DFU는 제품 범위와 M6 완료 조건에서 제외한다.
> 상태: USB 설치·안내는 구현됨. 공통 런타임 후보 7개 빌드·바이트 일치와 내장/외장 후보의 부분 교체·수신 사례를 확인했다. 연결 유지 구현은 확인했으나 재시작 재연결은 한 번 재시도해도 실패한 사례가 있어 안정화·제품 통합은 미완료다. [현재 검증 결과](#84-현재-검증-결과와-남은-작업)를 기준으로 한다.

조사 근거는 [§7](#7-구현-가능성-검토--2026-10-26), 개발·검증은 [§8](#8-개발검증-계획), 공통 런타임의 구성·확장 계약은 [§9](#9-공통-런타임-구축과-확장-설계)에 둔다. 현재 내장 4종의 배포 런타임은 같지만 `pairing_mode: 0`이다. 새 후보는 `open: 1`, `whitelist: 0`, `security_level: null`을 유지하고 `pairing_mode: 1`로 설치 모드를 활성화한다. 배포 설정은 아직 변경하지 않았다.

## 1. 목표와 현재 구현

프로그램 설치 화면은 USB를 기본으로 열고 Bluetooth를 선택 가능한 대안으로 제공한다. 앱이 해당 센서의 고정 프로그램을 전송하며, 설치 후 같은 실험실에서 측정용 연결·새 수신 확인으로 이어진다. 공식 micro:bit 모바일 앱 호출·파일 전달·복귀 안내는 M6에서 제외한다. 모든 시작 프로그램에서 무선 설치를 보장하는 것이 아니라, 지원 조건을 확인하고 불가능한 경우 USB로 돌아가는 흐름까지 제공한다.

처음에는 선택한 센서의 **공통 런타임 포함 HEX 하나**를 USB로 설치한다. 별도의 빈 런타임 설치 단계를 만들지 않는다. 이후 같은 런타임 계열의 프로그램끼리 무선으로 바꾸며, 런타임 자체가 바뀌면 USB로 새 계열을 설치한다. OS 본딩·PIN·기기 등록 삭제를 정상 사용 절차에 넣지 않는다. 브라우저의 장치 선택·권한 허용과 재연결은 필요하다.

| 이미 구현된 기반 | 재사용할 내용 |
|---|---|
| [USB 설치기](../src/device/programmer.js) | 파일 해시·V2 확인, 기록·저장 가드, 전송 진행·성공·실패와 정리 |
| [프로그램 목록](../src/device/firmware.js) | 다섯 센서의 고정 파일·버전·해시·codec·시작 명령 |
| [준비 진행](../src/guide/progress.js) | 앱이 관찰한 설치 결과와 기설치 사용자 확인 구분 |
| [측정 연결](../src/device/ble-client.js) | UART 측정 통신. 프로그램 전송 기능은 없음 |
| [USB 번들 빌드](../dev/usb-library/README.md) | 공식 연결 라이브러리 1.0.0의 USB·HEX 해석 export만 포함 |

설치용 Bluetooth 연결과 측정용 UART 연결은 별도 수명으로 다룬다. BLE 연결 성공만으로 프로그램 설치 가능 여부나 설치 완료를 판단하지 않는다.

## 2. 구현 전 확인할 기술 경계

2026-10-26 확인한 [공식 연결 라이브러리 지원표](https://microbit-foundation.github.io/microbit-connection/#platform-support)는 웹의 Bluetooth 연결은 지원하지만 **Bluetooth 프로그램 전송은 네이티브 Capacitor iOS/Android에서만 지원**한다고 명시한다. 현재 USB 번들에 Bluetooth export를 더하거나 PWA로 설치하는 것만으로 전송 기능이 생기지 않는다. 고정 1.0.0과 최신 문서의 API도 동일하게 취급하지 않는다.

이는 해당 라이브러리의 지원 범위다. 웹 부분 전송은 기존 PXT·공식 연결 라이브러리의 프로토콜을 참고한 개발 어댑터로 온도/밝기 전환을 확인했다. 제품 통합 시 검증된 부분 전송 로직과 출처·고정 버전을 재사용한다. 전체 DFU나 본딩 지원을 추가해서 비호환 런타임을 넘기지 않고 USB로 안내한다.

현재 [PXT 설정](../dev/firmware/pxt-template.json)은 UART용 open-link와 `pairing_mode: 0`을 사용한다. 전송 서비스 포함과 설치 모드 진입 가능성은 별도 조건이다. [§7.4](#74-makecode-페어링-모드와-기존-설정-이력)의 공식 진입 경로를 활용하되, 기존 연결 문제를 재현·비교한 뒤 설정 변경을 채택한다. 원본에서 가져온 BMP280 HEX는 따로 확인해야 한다. 무선 전송을 위해 HEX를 바꿀 경우 버전·해시·USB 설치·측정 호환성 및 이전 버전에서의 전환 방법을 함께 검증한다.

기존 프로그램이 전송 모드를 제공하지 않으면 USB 준비·복구가 필요할 수 있다. 버튼 진입 안내는 검증한 프로그램별로 제공한다. 모든 보드에서 최초 무선 설치가 가능하다고 안내하지 않는다. [공식 모바일 안내](https://microbit.org/get-started/user-guide/mobile/)의 전송 모드 설명은 참고 근거이며, 웹 전송 구현의 검증을 대신하지 않는다.

네이티브 앱 제작은 이번 방향 변경으로 확정하지 않는다. 웹 경로에서 해결할 수 없는 제약이 확인되면 근거와 대안을 정리해 제품 범위를 다시 결정한다. 외부 앱 안내로 임의 대체하거나 미구현 상태를 완료로 처리하지 않는다.

## 3. 설치 화면과 사용자 흐름

1. 선택한 실험의 프로그램 설치 화면은 **USB로 설치**가 기본이다. 보조 문구 **“선 없이 Bluetooth로도 설치할 수 있어요.”**와 **[Bluetooth로 설치]** 전환 버튼을 둔다. 지원 여부를 알고 있는 미지원 환경에서는 같은 자리에 이유·대안을 표시해 보드 조작부터 시키지 않는다. USB 자동 전송이나 자동 Bluetooth 전환은 하지 않는다.
2. Bluetooth 선택 시 **“이 앱의 프로그램으로 준비된 micro:bit는 무선으로 바꿀 수 있어요. 처음 준비할 때는 USB로 설치해 주세요.”**를 안내한다. 앱의 모드 전환 요청은 서비스와 장치 상태를 확인한 경우에만 사용한다. A+B를 누른 채 리셋하는 수동 진입은 실물 검증 뒤 보조 안내로 제공한다. 학생에게 런타임·부분 전송·보안 설정을 선택시키지 않는다.
3. 앱이 센서의 고정 파일과 해시를 준비한 뒤 사용자가 설치할 micro:bit를 선택한다. 장치 선택은 사용자 클릭에서 시작하고 현재 측정 연결과 설치 연결이 경쟁하지 않게 한다. 모드·서비스·등록된 런타임·프로그램 영역을 대조해 부분 전송 가능 여부를 판단한다. 비호환이면 쓰기 전에 **“이 프로그램은 USB로 한 번 설치해 주세요.”**와 **[USB로 설치하기]**를 제공한다.
4. 모드 진입이 안 되면 **“무선 설치 모드로 들어가지 않으면 USB로 설치해 주세요.”**와 **[USB로 설치하기]**를 제공한다. 브라우저 미지원·서비스 없음·프로그램 비호환·사용자 취소·전송 중 실패를 내부적으로 구분한다. 취소는 오류나 설치 성공으로 표시하지 않는다. 전송 중 실패에는 프로그램이 불완전할 수 있음을 짧게 알리고 **[다시 시도] / [USB로 설치하기]** 중 실제 복구 가능한 행동을 제공한다.
5. 전송 가능한 경우 진행·완료·복구 행동을 표시한다. 재부팅·재탐색 시 처음 선택한 보드임을 확인하고 임의의 첫 장치를 선택하지 않는다. USB로 돌아갈 때 설치 연결과 이전 작업을 정리하고 실험·센서·저장 자료를 유지한다. 브라우저에서 USB 직접 전송도 불가능하면 고정 HEX 파일 받기와 컴퓨터에서 USB로 옮기는 안내를 제공한다.
6. 전송 완료 후 설치 연결을 정리한다. 사용자가 **연결·수신 확인**으로 진행하면 측정용 연결을 새로 맺고 센서별 유효값·보정 흐름을 확인한다. 자동으로 기록을 시작하지 않는다.

기설치 사용자 확인과 보조 **프로그램 파일 받기**는 유지한다. 파일 다운로드는 수동 설치·복구용이며 외부 모바일 앱 연계를 위한 필수 단계가 아니다. 설치 가능 여부와 측정 가능 여부는 따로 판정한다. Bluefy 소개·주소 복사는 이미 구현된 측정 안내이며 Bluetooth 설치 지원의 근거가 아니다.

현재 미지원 iOS 측정 안내에는 [Bluefy 설치 링크](https://apps.apple.com/kr/app/bluefy-web-ble-browser/id1492822055)와 현재 주소 복사를 제공한다. Bluefy에서 다섯 센서의 연결·연속 수신·기록·저장은 실물 미검증이며, 이번 직접 설치 결정으로 지원 완료를 표시하지 않는다. 브라우저 간 저장 자료는 자동 이전되지 않으므로 실험 파일로 옮긴다.

## 4. M6 구현 순서와 완료 기준

| 구분 | 범위 | 완료 기준 |
|---|---|---|
| M6-1 | 환경별 안내·고정 HEX 다운로드 | 기존 manifest와 검증 규칙 재사용, USB 미지원 환경의 대안 제공, 다운로드를 설치 완료로 표시하지 않음 |
| M6-2 · 기반 검증 | 기존 연결 설정 이력·온도 비교 시험본·공식 설치 모드 | §8의 G0–G2. `pairing_mode` 한 설정의 영향을 분리하고 기존 측정 연결 유지·모드 진입/복귀를 실물 확인. 시험본의 USB 복구 가능 |
| M6-2 · 전송 검증 | 공통 런타임 확정·부분 전송·센서 확대 | §8의 G3–G4와 §9. 다섯 센서의 재현 가능한 빌드·동일 런타임·영역 일치, 파일 검증·중단 복구·대상 식별·새 측정 확인. 비호환은 USB 안내, 본딩/전체 DFU는 제외 |
| M6-2 · 앱 통합 | USB 기본·Bluetooth 선택·설치/복구·측정 연결 | §8의 G5. 저장·원자료 보존, 늦은 응답 차단, 브라우저별 지원·USB 복구와 파일 대안. 검증된 OS·브라우저·센서 범위만 공개 |

M6은 M5와 독립적으로 진행할 수 있다. Bluetooth 전송 검증은 M6-1 UI 완성을 기다리지 않아도 된다. 사용자용 화면 공개는 전송 검증과 상태 통합 후 진행한다. 앱 내부 무선 설치는 이제 M6-2의 완료 대상이며 별도 보류 목록이 아니다.

## 5. 모듈과 상태 계약

- 프로그램 파일 준비·해시·V2 적합성 검증은 USB·Bluetooth·파일 받기에서 공유하고 센서별 목록을 복제하지 않는다. 현재 USB 코드에서 실제로 함께 쓰는 부분만 분리한다.
- Bluetooth 설치 어댑터는 측정 Transport와 분리한다. 공통 UI에는 설치 상태·진행·결과를 전달하고 센서별 전송 조건은 프로그램 정의에 둔다.
- Controller는 기록 마감·저장 성공·측정 연결 해제를 조율한다. 전송 직전에도 설치 허용 조건을 다시 확인한다. 기록·미저장 자료가 있는 상태에서 설치가 이를 자동 종료하거나 버리지 않는다.
- 전송 프로토콜의 성공 조건을 충족해야 앱이 관찰한 설치 결과를 남긴다. 진행률 100%, GATT 쓰기 완료, 예상치 못한 연결 해제, 재탐색만으로 성공을 만들지 않는다. 확인 불가·중단은 성공과 구분한다.
- 설치 결과·기설치 사용자 확인·장치가 보고한 프로그램 버전·새 수신 확인은 별도 사실이다. 숫자 UART 값만으로 설치 버전이나 설치/측정 장치의 동일성을 확정하지 않는다.
- 전송 중 취소·탭 숨김·연결 끊김은 채택한 프로토콜의 중단·복구 조건에 맞춰 처리한다. 안전한 중단을 보장하지 못하면 임의 중간 취소 버튼을 제공하지 않는다. 이전 비동기 응답이 새 설치의 성공을 만들지 않게 한다.
- 원본 라이선스·고정 버전·출처·자산 해시를 보존하고, 현재 USB·측정 경로에 불필요한 의존성을 추가하지 않는다.

## 6. 실기기 인수와 검증 범위

첫 대상은 외장 배선이 없는 **내장 온도**이며, 기존 배포본과 비교 시험 후 다섯 센서로 넓힌다. 다음 항목은 Bluetooth 설치 관점에서 아직 미검증이다. 기존 [USB·측정 실물 기록](history/hardware-acceptance-2026-10-19.md)을 무선 전송의 근거로 사용하지 않는다.

| 대상 | 확인할 내용 |
|---|---|
| 환경·원본 프로그램 | OS·브라우저 버전, 전송 구현 버전, 보드 리비전, 기존/대상 HEX 버전·해시. 출고/MakeCode/Python/우리 센서 프로그램에서 전송 모드·서비스 차이 |
| 전송·재설치 | 내장 온도 최초 전송, 같은 프로그램 재설치, 다른 센서로 변경·복귀, 전송 후 측정 UART·단위·자기장 보정 유지 |
| 장치 선택 | 여러 보드 중 선택 대상만 변경, 재부팅 뒤 재탐색에서 대상 유지. 해당 구현에서 식별을 보장할 수 없는 경로는 제공하지 않음 |
| 실패·복구 | 선택 취소·권한 거부·단절·배터리 부족·탭 숨김/종료·재시도·USB 복구. 실패를 성공으로 표시하지 않음 |
| 자료·수업 흐름 | 기존 저장 자료·분석 초안 보존, 설치 연결 정리 후 측정 연결·새 수신·기록·저장·분석. 자동 기록 시작 없음 |
| 브라우저별 지원 | Web Bluetooth API 존재뿐 아니라 전송 서비스 접근·권한·재탐색을 실제 검증. Bluefy도 별도 확인 전 설치 지원으로 표시하지 않음 |

기존 programmer·준비 진행·파일 검증·저장 보존 테스트를 보완하되, 모의 전송은 실물 설치 완료의 근거로 쓰지 않는다. 구현·검증 결과는 [기획](unified-sensor-lab-plan.md)과 [기술 설계](unified-sensor-lab-architecture.md#63-usb-설치식별)의 해당 계약에 반영한다.

## 7. 구현 가능성 검토 — 2026-10-26

**현재 판정:** 공통 런타임 안의 부분 전송을 제품 경로로 채택한다. 아래 배포 HEX 분석은 정적 근거이고, 시험본의 실물 결과는 §8.4에 별도로 기록한다. 기존 BMP280 HEX는 비호환이므로 최초 전환은 USB다. BMP280를 공통 런타임으로 새로 빌드한 뒤에는 내장 센서와 부분 전송으로 전환하도록 설계한다. 전체 DFU로 비호환을 해결하는 이전 계획은 폐기했다.

### 7.1. 성립 조건과 반례

현재 보드 상태를 S, 대상 프로그램을 T라 할 때 제품에 제공할 전송은 다음 조건을 모두 확인해야 한다. 이는 확인 의무의 분해이며 하드웨어 동작의 형식 증명은 아니다.

| 조건 | 확인한 근거 / 남은 부분 |
|---|---|
| 브라우저 통신 | Web Bluetooth의 GATT 쓰기·알림으로 프로토콜을 구현할 수 있다. HTTPS·사용자 장치 선택·허용 서비스 선언이 필요하다. API가 없는 브라우저에서는 이 웹 경로가 성립하지 않는다. |
| 보드의 전송 서비스·모드 | CODAL V2와 내장 센서의 생성 빌드 설정에는 부분 전송·DFU가 포함되어 있다. 다만 현재 `pairing_mode: 0`은 표준 부팅 진입 경로를 끈다. 서비스 접근과 안전한 설치 모드 진입은 각각 확인해야 한다. |
| S→T 호환성 | 부분 전송은 런타임 해시·프로그램 시작 주소 일치가 필요하다. 이번 HEX 비교로 내장 4종의 상호 호환 조건을 확인했고 BMP280와의 불일치를 확인했다. |
| 패킷·무결성 | 부분 전송은 20바이트 패킷 4개당 64바이트 자료와 ACK/재전송을 사용한다. 배포 파일 SHA-256, 영역 검사, 전송 완료·재연결 식별·새 수신을 구분한다. 전체 DFU의 객체 CRC/SHA 검증을 부분 전송도 제공한다고 주장하지 않는다. |
| 동일 보드 유지 | 전송 모드 전환·재부팅 뒤 선택한 대상임을 확인해야 한다. 웹의 장치 식별자를 네이티브 MAC 주소와 동일하게 취급할 수 없고, 주변 첫 보드로 자동 연결해서는 안 된다. |
| 실패 복구 | CODAL 부분 전송 소스에는 미완료 표시가 있고 부팅 시 복구 모드 진입은 `pairing_mode` 조건 안에 있다. 현재 배포본에서 자동 복구가 작동한다고 주장하지 않는다. 수정 후보에서도 전원 차단·재전송·새로고침을 검증하며, 실패 전 프로그램의 보존을 보장하지 않는다. USB 복구를 유지한다. |
| 설치 후 실행 | 전송 연결을 정리한 뒤 측정용으로 다시 연결하고 프로그램·센서 조건을 확인한다. UART 숫자 수신만으로 정확한 프로그램 버전을 증명할 수 없다. |

반례: 전송 서비스를 제공하지 않는 보드 상태, Web Bluetooth가 없는 브라우저, 런타임이 다른 두 프로그램의 부분 전송. 따라서 “모든 보드·모든 브라우저에서 USB 없이 설치”는 현재 목표의 보장 문구로 사용할 수 없다. 표준 Safari·Firefox는 현재 API 미지원이고 Windows/macOS Chromium·Android Chrome은 우선 실물 검증 후보다. Bluefy의 API 제공과 우리 전송 기능의 검증은 별개다. [브라우저 호환 자료](https://github.com/mdn/browser-compat-data/blob/main/api/Bluetooth.json), [Chrome API·권한 안내](https://developer.chrome.com/docs/capabilities/bluetooth)

### 7.2. 배포 HEX의 직접 비교

현재 [설치 허용 목록](../src/device/firmware.js)의 파일 5개를 읽었다. 정규화 SHA-256이 manifest와 모두 일치했고, 고정 공식 HEX 해석기로 V2 부분을 분리했다. nrf-intel-hex 결과와 별도의 Intel HEX 레코드 해석을 대조하여 51,977개 레코드의 길이·체크섬·주소 및 5개 메모리 맵의 바이트 일치를 확인했다. 배포 파일은 변경하지 않았다.

| 대상 | PXT 시작 주소 | 런타임 식별 해시 | 코드 영역 파일 자료 / 64바이트 정렬 |
|---|---|---|---|
| 내장 온도 | 0x49000 | 11f3cd7e54807276 | 4,320 / 4,352 B |
| 내장 밝기 | 0x49000 | 11f3cd7e54807276 | 4,496 / 4,544 B |
| 내장 가속도 | 0x49000 | 11f3cd7e54807276 | 4,528 / 4,544 B |
| 내장 자기장 v2 | 0x49000 | 11f3cd7e54807276 | 5,232 / 5,248 B |
| BMP280 | 0x49000 | cc86c4c300ffc9b1 | 16,912 / 16,960 B |

메모리의 0x1C000 이상·0x49000 미만을 바이트 비교했다. 내장 4종의 6개 조합은 차이 0바이트이며 공통 SHA-256은 `e592fde1da441662133f245eb52248a53eca3af3f1aabe7660f910c70c2e362f`다. BMP280와 각 내장 프로그램은 그 범위에서 174,417바이트가 다르다. 시작 주소만 같다고 부분 전송을 허용하면 안 된다.

위 코드 크기는 HEX 텍스트 크기나 실제 무선 패킷 총량이 아니다. 헤더·응답·재전송 비용과 연결 시간을 포함하지 않으며 속도·완료 시간을 추정하지 않았다. 이 판정은 조사한 파일 버전에만 유효하다. 연결한 보드가 실제로 같은 런타임인지 다시 읽어야 한다.

5개 파일의 0x77000 이상·0x7E000 미만을 0xFF로 빈 주소를 채워 비교한 부트로더 영역 SHA-256도 `b99e57be2995e3c50881a0b1b167ffdae6e22292b0ce3ff155ce546ccfef1f37`로 같고 `microbit_app` 표식이 있다. 이는 전체 DFU 후보를 뒷받침하지만 현재 보드의 부트로더 버전·실행 동작을 증명하지 않는다. UUID 공통 바이트열의 존재도 실제 GATT 서비스 노출의 증거로 대신 쓰지 않는다.

### 7.3. 재사용 후보와 검증할 차이

부분 전송 구현은 현재 설계의 근거다. 아래 전체 DFU 후보·init 조사 내용은 방향 결정 전의 비교 이력이며 제품 구현 대기 목록이 아니다.

| 후보 | 근거 | 판단 |
|---|---|---|
| Microsoft PXT의 웹 부분 전송 | [webble.ts](https://github.com/microsoft/pxt/blob/3acf314d7956dd158d449cc493df68c115d7585f/pxtlib/webble.ts)는 GATT 알림, 런타임 해시 비교, BLE 모드 전환, 재전송을 구현 | 웹 경로의 실제 선례다. PXT 내부 의존·구형 writeValue 사용·V2 Universal HEX 처리를 검토해야 하므로 그대로 이식하지 않음 |
| 공식 연결 라이브러리 | [부분 전송](https://github.com/microbit-foundation/microbit-connection/blob/12cbc608be4f5cfb0496b822ae6636389d8b97a4/packages/microbit-connection/src/bluetooth/flashing/flashing-partial.ts), [서비스](https://github.com/microbit-foundation/microbit-connection/blob/12cbc608be4f5cfb0496b822ae6636389d8b97a4/packages/microbit-connection/src/bluetooth/services/partial-flashing-service.ts) | 패킷 처리·호환 판정의 참고 구현. 공개 웹 연결 경로에는 부분 전송 optionalServices가 빠져 있고 모드 전환·bond 처리는 네이티브 경로에 의존한다. 전체 전송은 Nordic Capacitor 플러그인으로 연결되어 패키지 교체만으로 지원되지 않음 |
| thegecko/web-bluetooth-dfu | [Secure DFU 구현](https://github.com/thegecko/web-bluetooth-dfu/blob/95fd509a5279ae4463f3e12f1cd21565e870027c/src/secure-dfu.ts), MIT, package 1.2.1. 조사 시 기본 브랜치 마지막 커밋은 2024-01-11 | 종료한 전체 DFU 조사의 참고 구현. CRC 함수 미제공 시 검사 생략, 구형 쓰기 API·재탐색 처리 등의 차이 때문에 그대로 채택하지 않았으며 제품 편입 대상에서 제외 |
| NordicPlayground/secure-dfu-web-bluetooth | [저장소](https://github.com/NordicPlayground/secure-dfu-web-bluetooth/tree/610ff25f026264c05faba7baf405c41048e4b38d), BSD-3-Clause. 마지막 커밋 2016-10-28, 사용법 TODO | 프로토콜 참고용. 유지 상태를 고려해 우선 채택 대상으로 삼지 않음 |

공식 패키지의 최신 조사 소스와 우리 USB 번들 1.0.0은 다르다. 기존 USB 번들을 그대로 두고 필요한 웹 어댑터의 실제 재사용 범위를 먼저 검증한다. 위 후보를 설치하거나 앱 의존성에 추가하지 않았다.

부분 전송의 런타임/앱 식별 해시는 메모리에 저장된 표식에서 읽는다. 이 값의 일치가 전송된 전체 내용을 다시 해시해 확인한 결과는 아니다. CODAL의 완료 명령도 전체 이미지 암호학적 검증 결과를 반환하지 않는다. ACK·완료·재부팅·앱 동작을 구분하고, 더 강한 설치 식별이 필요하면 장치의 명시적 버전 응답 등 추가 계약을 검토한다. [CODAL 메모리 맵](https://github.com/lancaster-university/codal-microbit-v2/blob/f5d1682fc3882022d3d5a7facb1fddb4b0ea7b52/source/MicroBitMemoryMap.cpp), [전송 서비스](https://github.com/lancaster-university/codal-microbit-v2/blob/f5d1682fc3882022d3d5a7facb1fddb4b0ea7b52/source/bluetooth/MicroBitPartialFlashingService.cpp)

전체 DFU는 Universal HEX를 그대로 GATT로 보내는 작업이 아니다. V2 애플리케이션 영역과 전용 init 자료가 필요하다. 공식 구현은 `microbit_app` 형식·크기·역순 SHA-256으로 56바이트 init 자료를 만들며, V2 부트로더에도 이 형식을 읽는 코드가 있다. Secure DFU라는 이름을 전자서명 검증 보장으로 해석하지 않는다. SHA-256 검사를 생략하는 분기는 채택하지 않는다. [공식 init 생성 코드](https://github.com/microbit-foundation/microbit-connection/blob/12cbc608be4f5cfb0496b822ae6636389d8b97a4/packages/microbit-connection/src/bluetooth/flashing/nordic-dfu.ts), [V2 부트로더](https://github.com/microbit-foundation/v2-bootloader/blob/4215a2beb79e30f9c1435965235512353fcd4c9a/nRF5SDK_mods/components/libraries/bootloader/dfu/nrf_dfu_validation.c)

확인한 [GATT 차단 목록](https://github.com/WebBluetoothCG/registries/blob/228b62c31c177c9b770b79896aec9ef660f62216/gatt_blocklist.txt)과 [Chromium 기본 목록](https://github.com/chromium/chromium/blob/main/content/browser/bluetooth/bluetooth_blocklist.cc)은 Nordic Legacy DFU(00001530…)를 차단한다. 부분 전송 UUID(e97dd91d…)와 V2 Secure DFU(0xFE59)는 이 목록에 없었다. 다만 Chromium은 추가 차단 목록도 적용할 수 있고 OS·권한·GATT 접근은 별도다. 차단 목록에 없다는 사실만으로 실물 성공을 확정하지 않는다.

### 7.4. MakeCode 페어링 모드와 기존 설정 이력

MakeCode의 표준 Bluetooth 설치 모드는 센서 `main.ts`에 복사하는 일반 블록이 아니라 함께 빌드되는 CODAL 런타임 기능이다. 조사 대상은 현재 내장 펌웨어의 CODAL V2 v0.3.5 소스이며, 다른 런타임을 쓰는 BMP280에 같은 판정을 자동 적용하지 않는다.

| 역할 | 확인한 코드·조건 |
|---|---|
| 부팅 시 진입 | [MicroBit::init()](https://github.com/lancaster-university/codal-microbit-v2/blob/f5d1682fc3882022d3d5a7facb1fddb4b0ea7b52/model/MicroBit.cpp#L210). `DEVICE_BLE`와 `MICROBIT_BLE_PAIRING_MODE`가 켜진 경우 A+B, `RebootMode`, `flashIncomplete`를 처리하고 `pairingMode()`로 진입. 일반 부팅은 측정 프로그램 실행으로 진행 |
| 앱 요청으로 진입 | [restartInBLEMode()](https://github.com/lancaster-university/codal-microbit-v2/blob/f5d1682fc3882022d3d5a7facb1fddb4b0ea7b52/source/bluetooth/MicroBitBLEManager.cpp#L931)가 재부팅 표식을 저장. 부분 전송 서비스의 `MICROBIT_RESET` 요청에서 사용하며, 재부팅 후 위 진입 경로가 활성화되어 있어야 함 |
| 모드 화면·대기 | [pairingMode()](https://github.com/lancaster-university/codal-microbit-v2/blob/f5d1682fc3882022d3d5a7facb1fddb4b0ea7b52/source/bluetooth/MicroBitBLEManager.cpp#L726). 광고·Bluetooth 표시·보드 식별 패턴·연결 대기. DFU 부트로더 진입 및 실제 전송 완료와는 별도 단계 |
| 전송·보안 | `MICROBIT_BLE_PARTIAL_FLASHING`·`MICROBIT_BLE_DFU_SERVICE`와 실제 접근 권한을 확인. [보안 설정](https://github.com/lancaster-university/codal-microbit-v2/blob/f5d1682fc3882022d3d5a7facb1fddb4b0ea7b52/source/bluetooth/MicroBitBLEManager.cpp#L276)은 별도로 적용되므로 설치 모드 활성화와 평상시 페어링 강제는 같은 의미가 아님 |

**기존 설정의 이유:** 2026-06-19 [29cfc02](https://github.com/Cho-WH/MicrobitSensorDashboard/commit/29cfc02fed90f18789a707dc99282996ac4306d6)는 MakeCode의 No Pairing Required 선택 후에도 GATT 연결이 안정되지 않을 때 `enabled: 1`, `open: 1`, `pairing_mode: 0`, `whitelist: 0`, `security_level: null`을 함께 쓰도록 기록했다. 당시 문서는 예전 페어링 정보와의 충돌 회피를 이유로 들었다. 2026-10-20 [5d8be85](https://github.com/Cho-WH/MicrobitSensorDashboard/commit/5d8be857f37cbba0b3b86c88e666d1fb561307a2)는 현재 공통 빌드 설정에 이 조합을 포함했다.

찾은 이력에는 `pairing_mode` 하나만 바꾼 비교 결과나 원인 로그가 없다. **연결 문제 회피가 목적이었다는 사실과, `pairing_mode: 1` 자체가 원인이었다는 주장을 구분한다.** 고정 MakeCode 9.1.1의 [core 설정](https://github.com/microsoft/pxt-microbit/blob/59408da502b825423ad2b0180bcf105927e7def0/libs/core/pxt.json)에서 No Pairing Required는 open·whitelist·security_level을 조정하며 pairing_mode를 끄지 않는다. 공식 모드 활성화와 기존 측정 연결의 양립은 타당한 후보지만 실물 회귀 없음까지 증명된 것은 아니다.

현재 온도 생성 설정은 `MICROBIT_DAL_BLUETOOTH_PAIRING_MODE=0`, 부분 전송·DFU=1이다. 따라서 서비스 포함만으로 표준 모드 진입·중단 후 복구가 준비됐다고 판단하지 않는다. **배포 설정은 유지하고, 온도 시험본에서 pairing_mode만 1로 바꾸어 비교한다.** 다른 보안 설정·프로토콜·센서 코드는 함께 바꾸지 않으며, 실패하면 측정 연결과 설치 모드 중 어느 단계가 실패하는지 분리해 원인을 확인한다.

## 8. 개발·검증 계획

**상태: G1 시험본 준비·G2 핵심 실물 시험 통과, G3 부분 전송 구현 및 온도→밝기→온도 실물 전환 확인.** [시험실 실행·제한·검사](../dev/bluetooth-install/README.md)에 고정 빌드 후보 7개를 전송하는 웹 어댑터와 자동 시험·로컬 명령 통로를 구현했다. 새 후보의 실물 검증 완료를 뜻하지 않는다. 파일 해시·헤더와 전송 직전 보드 상태·런타임·영역을 확인하고, 블록 응답과 종료 요청 뒤 재연결 식별을 구분한다. 중간 단절·전원 차단 후 복구와 센서 확대는 미완료이므로 G3 전체 통과로 표시하지 않는다. 정식 앱 메뉴·배포 대상에서도 제외된다. 사용자 결정에 따라 장시간 수신·반복 재연결과 첫 UART 전환 오류 해결은 이번 가능성 시험의 선행 조건에서 제외하고, 실제로 막히면 해결한다. M2·M4의 기존 완료 판정은 유지한다.

### 8.1. 단계별 산출물과 통과 조건

**현재 순서:** 기존 G0–G3 증거를 유지한다. 내장 4종·BMP280·아날로그 기반의 공통 후보 빌드와 정적 비교는 완료했으며, 새 후보 실물 전환·수신 → 중단 복구 → 앱 통합을 진행한다. G4는 종전의 전체 DFU 시험에서 **공통 런타임·전 센서 호환 검증**으로 변경한다. 본딩 후보 제작과 전체 DFU 성공은 선행 조건이 아니다. 개발 페이지의 전체 DFU 코드·자동 검사·실패 로그는 조사 자산으로 보존하며 제품 경로에는 포함하지 않는다.

| 단계 | 개발·검증 작업 | 통과 조건·실패 시 처리 |
|---|---|---|
| G0 · 기준선 | Windows Chrome + V2 + 배포 온도 HEX로 현재 UART 연결·수신·재연결과 버튼 진입 결과 기록. 프로그램 쓰기·리셋 요청 없이 전송 서비스·상태·런타임을 조회하는 개발용 진단 준비. OS 페어링 기록과 브라우저 장치 권한은 따로 기록 | 기존 측정 경로가 정상이고 재현 조건·원본 해시 확보. 과거와 같은 오류가 나면 로그를 보존한 뒤 원인 비교. 처음부터 페어링 기록을 모두 삭제해 실패 조건을 없애지 않음 |
| G1 · 비교 후보 | 온도 A=현재 배포본, B=동일 센서 소스·도구 버전에서 pairing_mode만 1인 후보. 새 네이티브 이미지·compile key·해시·라이선스와 실제 설정 확인. 소스·설정 내장값, V2 해석과 변경 영역 비교 | 허용한 설정 외 의미상 변경이 없고 재현 가능한 후보 확보. 네이티브 이미지가 달라지는 것은 예상 변화이며 별도 기록. 기존 캐시를 새 설정인 것처럼 재사용하거나 실패를 해시 갱신으로 우회하지 않음 |

| G3 · 부분 전송 | G2 통과 후 같은 설정으로 밝기 후보 생성, 런타임·시작 주소 재비교. 같은 프로그램 재설치 → 온도→밝기→온도. ACK·재전송·완료 처리와 중간 단절·재부팅 복구 확인 | 호환되는 후보 사이 실제 전송·복귀 성공, 비호환 판정 시 쓰기 0회. 중단을 성공으로 표시하지 않고 재시도 또는 USB 복구 가능. 통과 후 가속도·자기장 후보와 양방향 전환 확대 |
| G4 · 공통 런타임·전 센서 | §9의 고정 프로필·허용 의존성·호환 목록 생성. 가속도·자기장 확대, BMP280 원본 코드/의존성 확인 및 새 도구로 빌드. 다섯 센서가 같은 런타임·시작 주소를 쓰는지 검사하고 대표 왕복 전환·수신 확인 | 다섯 센서의 재현 가능한 빌드와 정적 상호 호환, 실제 내장 4종 전환·BMP280↔내장 전환 및 센서별 측정 계약 확인. 다른 런타임은 쓰기 없이 USB 안내. BMP280 미편입을 완료로 표시하지 않음 |
| G5 · 앱·환경 | 검증한 전송을 설치 어댑터로 통합. §3의 USB 기본·Bluetooth 선택, 측정/저장 가드, 취소·오류·USB 복구 구현. Android Chrome과 공개 지원할 다른 브라우저, 보드 2대 이상 조건 검증 | §6·§8.3의 계약 통과. 지원 범위·제한·펌웨어 버전·복구 방법 기록 후 배포. 실기기 미검증 환경은 지원 완료로 표시하지 않음 |

G0 진단은 개발용으로 한정하고 제품 화면에 내부 메모리 정보·프로토콜 용어를 노출하지 않는다. G2의 자동 모드 전환이 실패해도 검증된 버튼 진입으로 전송할 수 있다면 그 경로를 별도로 평가한다. G3만 성공하면 내장 센서 부분 전송 가능성만 확인한 것이며, 전체 M6 완료로 확대하지 않는다.

### 8.2. 페어링 설정 A/B 비교

A/B는 같은 보드·전원·OS/브라우저·앱 버전에서 비교한다. USB 설치 자체가 보드의 연결 기록에 영향을 줄 수 있으므로 **각 설치 뒤 실제 보드·OS·브라우저 상태를 기록**한다. “오래된 페어링 있음”을 보드 기록까지 같다는 뜻으로 사용하지 않는다. 재현하지 못한 과거 오류는 해결됨이 아니라 미재현으로 남긴다.

| 조건 | A: 현재 배포본 | B: pairing_mode=1 후보에서 확인할 것 |
|---|---|---|
| OS에 기존 페어링 기록이 있는 환경 | 삭제 전 연결·서비스 탐색·알림 구독·start 응답·재연결을 기록 | 같은 조건에서 비교. 실패하면 어느 단계·오류인지 기록하고 그 뒤에만 기록 정리 전후를 비교 |
| OS 페어링 기록 없는 환경 | 브라우저 권한이 없는 첫 선택과 이미 허용된 재연결을 구분 | 평상시 PIN·OS 사전 페어링 없이 기존 UART 흐름이 유지되는지 |
| 보통 부팅·리셋 | 기존 측정 기준선 | 불필요하게 설치 모드에 머물지 않고 명시적 시작 명령을 기다리는지 |
| A+B 유지 후 리셋 | 현재 진입 여부를 기록 | LED 표시·식별 패턴과 조회 모드 일치, 사용자가 복귀 후 측정 가능 |
| 앱에서 모드 전환 요청 | 서비스 조회까지만 수행; 꺼진 진입 경로에 쓰기 실험을 강행하지 않음 | 요청→재부팅→동일 보드 재연결→모드 확인. 실패·단절을 성공으로 취급하지 않음 |
| 설치 모드 진입·복귀 후 다시 측정 | 비교 가능한 일반 재연결 기준 | 자동 기록·이전 start 재실행 없이 새 시작/중단·정상 수신 |

이번 가능성 시험에서는 사용자 결정에 따라 **5분 연속 수신·재연결 3회를 요구하지 않는다.** 설치 모드 진입·복귀와 복귀 후 온도 수신을 우선 확인한다. 장시간 안정성·반복 재연결은 제품 통합 단계에서 영향에 맞게 검증하고, 짧은 수신 성공을 장시간 안정성 보증으로 확대하지 않는다.

### 8.3. 자동 검사와 실물 인수의 역할

| 변경 범위 | 기존 검사에 보완할 계약 | 별도로 필요한 실물 확인 |
|---|---|---|
| 펌웨어 후보·공통 설정 | `firmware-build.test.mjs`, `firmware.test.mjs`: 캐시 키·출처·해시, 내장 소스/설정, V2·배포 버전 가드. `builtin-sensors.test.mjs` 등 실제 영향받는 센서 규약 | 위 A/B 비교, USB 설치·복구, 온도·밝기 단위와 값, 가속도 mg·자기장 선택/보정·BMP280 시작 명령과 채널 유지 |
| 설치 어댑터·전송 | 기존 programmer·부분 전송 검사: 파일 SHA-256·런타임·시작 주소·상한 불일치 시 쓰기 금지, ACK/재전송·종료·오류 전파·연결 정리. 긴→짧은 프로그램과 손상된 프로그램 헤더의 복구 거부/USB 안내 | 실제 전송·재부팅·재연결·새 수신. 모의 전송 통과를 무선 설치 성공으로 기록하지 않음 |
| Controller·UI | `guide.test.mjs`, 관련 브라우저 준비/연결 suite: 기록·미저장 상태의 설치 차단, 늦은 응답·중복 클릭 차단, USB 전환, 취소/미지원/실패 구분 | 보드 조작 안내의 일치, 실제 선택 취소·권한 거부, 지원 환경과 미지원 환경의 대안 |
| 설치 후 측정 | `device-ble.test.mjs`, `device-transport.test.mjs` 등 변경된 연결 경로만: 연결 유지 인계·재시작 후 재연결·명시적 시작, 이전 콜백/샘플 무효화 | 시작·중단·수신·기록·저장·분석까지 연결, 저장 자료·분석 초안 보존 |

전송 단계에서는 초반·중간·완료 직전의 연결 단절/전원 차단, 탭 숨김/종료, 재시도·USB 복구를 구분해 기록한다. 실제 전원 차단은 복구 가능한 시험 보드와 원본 HEX를 준비한 상태에서 수행한다. 보드가 2대 이상일 때 설치 대상 외의 보드는 변경되지 않아야 한다. 대상 동일성이 불명확하면 쓰기를 중단하고 재선택·USB 안내로 처리한다.

검사는 [AGENTS.md](../AGENTS.md)에 따라 변경 범위별로 실행한다. 작업 중 전체 검사를 관행적으로 실행하지 않으며 기존 유효 검사를 약화하지 않는다. 개발 페이지의 진단 계약은 `bluetooth-diagnostics.test.mjs`와 `bluetooth-diagnostics.spec.mjs`에서 보호한다. 일회성 조사 스크립트는 정리하고, 재사용할 진단·회귀 검사는 정식 경로에 통합한다.

### 8.4. 현재 검증 결과와 남은 작업

2026-10-26 기준. 최근 시험 환경은 Windows Chrome 155·micro:bit V2 [gugav], 공통 시험 런타임은 5f21a4c8e2b240e5다. 아래는 개발 페이지에서의 실물 관찰이며 정식 앱 통합·지원 환경 확정·M6 완료를 뜻하지 않는다.

**현재 판단:** 공통 런타임 안의 무본딩 부분 교체와 센서 수신은 가능하다. 진단↔측정 및 성공한 시험 사이의 연결 유지는 확인했다. 그러나 재시작 뒤 재연결은 불안정하며, 연결·조회 재시도 한 번으로도 복구하지 못한 사례가 있다.

**최신 실물 상태:** 온도 파일 전송과 종료 후 해제 이벤트까지 확인했으나, 마지막 프로그램 식별·일반 실행·측정 수신은 미확인이다. 조건부 후속 내장 왕복·BMP280·아날로그 시험은 시작하지 않았다. 과거 성공 기록으로 이 마지막 실패를 덮어쓰지 않는다.

**현재 개발 코드와 합의된 후속 방향**

- 구현: 진단↔UART 및 시험 성공 종료 시 연결 유지. 재시작의 해제 이벤트를 최대 6초 기다린 뒤 연결·조회. 이 연결·조회가 실패하면 기존 1.2초 복구 간격 후 한 번 재시도. 실패·취소·사용자 해제 시 정리. 임시 독립 관찰자는 모듈 정리 후에도 유지한다.
- 미구현: 이벤트 미수신 시 대기를 줄이고 연결 정리→자동 재연결·상태 조회로 이어가는 경로. 현재는 이벤트 시간 초과에서 시험이 중단된다.
- 최종 판정은 보드 응답, 원하는 모드, 런타임·프로그램 식별값으로 한다. 이벤트·전송 100%만으로 성공을 판정하지 않는다. 재연결 복구에서 모드 명령·펌웨어 전송을 반복하지 않으며, 제한된 복구 실패 시 USB로 안내한다. 1–2초 복구를 보장하지 않는다. 상세 계약은 [기술 설계 §6](unified-sensor-lab-architecture.md#6-장치-통신과-펌웨어)에 둔다.

**남은 검증**

1. 이벤트 미수신과 실제 단절을 나눠 제한된 복구·실패 종료를 확인한다. 원인을 끝까지 규명하는 것을 구현의 선행 조건으로 삼지 않는다.
2. 안정적인 기본 왕복 뒤 외장 후보 반복, 알려진 아날로그 입력·BMP280 기준 계측 비교, 중단/USB 복구, 다른 보드·브라우저를 확인한다.
3. 설치 취소의 명시적 일반 모드 복귀는 이벤트 시간 초과가 남아 있는 후순위 항목이다. [기존 시험](../dev/bluetooth-install/results/2026-10-26-gugav-disconnect-event.json).

연결 계약 변경 후 타입 검사·단위 검사·빌드와 무선 설치 브라우저 검사가 통과했다. 이후 일회성 연결 시간 시험과 중복 브라우저 검사를 정리했다. 전체 브라우저 검사는 사용자 요청으로 중단했으므로 전체 통과로 기록하지 않는다. 모의 검사 통과는 위 실물 재연결 실패의 해결을 뜻하지 않는다.

배포 HEX·manifest·기존 캐시는 변경하지 않았다. 채택 시 새 버전·해시·출처를 등록하고 기존 저장 자료의 펌웨어 사본·이어 측정 계약을 보존한다. 런타임 계열 변경·비호환은 USB로 처리한다. 전체 DFU는 이전 [zivuz] 시험에서 본딩형 진입 알림 구독 중 실패해 데이터 전송 전에 중단했고, 사용자 결정으로 제품 범위에서 제외했다.

## 9. 공통 런타임 구축과 확장 설계

2026-10-26 조사·설계와 첫 구현 결과다. 로컬 다중 소스 빌드·BMP280 수정 후보·아날로그 원시 입력·7종 런타임 비교는 구현·자동 검증했다. 제품 배포·새 후보 실물 검증·임의 외부 확장/다른 런타임 프로필 지원은 미완료다.

### 9.1. 고정할 부분과 교체할 부분

공통 런타임은 MakeCode/CODAL의 네이티브 기능과 Bluetooth 설치·연결 설정이다. 센서별 측정 루프·보정 계산·통신 명령 처리 및 기존 API를 이용하는 TypeScript 드라이버는 프로그램 영역에 둔다. 부분 교체는 이 영역의 새 실행 이미지를 설치하는 방식이며 변경 줄만 덧대는 패치나 실행 중 모듈 로딩이 아니다. 프로그램 추가 후 재부팅하며 동시에 하나의 센서 프로그램을 실행한다.

확장성의 기준은 **여러 센서를 지원하는 안정된 입출력 API와 재현 가능한 빌드**다. 모든 센서 드라이버를 런타임에 선탑재하거나 미래의 모든 C++ 확장을 미리 넣지 않는다. 필요한 네이티브 기능이 바뀌면 새 런타임 계열을 발행하고 USB로 전환할 수 있어야 한다. 영구적인 무선 호환성을 약속하지 않는다.

PXT는 C/C++·어셈블리 파일, 생성 설정·함수 테이블과 컴파일 서비스 정보를 모아 네이티브 compile key를 만든다. 따라서 TypeScript 파일만 수정해도 전이 의존성이나 빌드 설정이 달라지면 호환성을 다시 확인해야 한다. 같은 도구 버전이나 같은 패키지 이름만으로 런타임 동일성을 보장하지 않는다. [고정 PXT 13.0.1의 빌드 입력·해시 생성](https://github.com/microsoft/pxt/blob/v13.0.1/pxtlib/cpp.ts)

### 9.2. 공통 기능의 범위

|---|---|---|

### 9.3. 확장 패키지 편입 규칙

1. 우선 기존 core API를 쓰는 TypeScript 드라이버를 재사용한다. 확장의 `files`뿐 아니라 전이 의존성, C/C++/어셈블리, `yotta`/CODAL 설정, 조건부 파일·대상별 설정을 조사한다. TypeScript 중심 확장도 이 경로에서 런타임을 바꿀 수 있다.
2. 네이티브 기능이 꼭 필요하면 실제 사용하는 확장들의 공통 집합을 정하고 **모든 센서가 같은 네이티브 입력**으로 빌드되도록 한다. 센서마다 별도 런타임을 만들고 같은 계열 이름을 붙이는 방식은 금지한다.
3. MakeCode의 `cppDependencies`는 선택적인 패키지의 C++ 부분을 미리 포함해 나중에 패키지를 추가해도 네이티브 재컴파일을 피하도록 마련된 기능이다. 고정 PXT에도 처리 코드가 있다. 필요할 때 사용할 수 있는 후보이며, 현재 앱의 빌드 프로필에서는 아직 채택·검증하지 않았다. 먼저 작은 후보로 사용/미사용 프로그램의 compile key·런타임 바이트 동일성을 확인한다. [공식 설명](https://makecode.com/extensions/pxt-json#c-dependencies), [고정 구현](https://github.com/microsoft/pxt/blob/v13.0.1/pxtlib/package.ts)
4. 공통 기능의 포함과 실행은 구분한다. 실제 센서의 연결·버스 초기화는 그 센서를 사용하는 프로그램에서 수행하고, 장치가 없을 때 부팅·설치 모드·다른 센서가 막히지 않아야 한다. 핀·타이머·메모리·GATT 자원 충돌을 함께 검토한다.
5. 패키지는 정확한 커밋·전이 의존성·내용 해시·라이선스로 고정한다. `core: "*"`는 고정 target에 번들된 것을 뜻하도록 현재 빌드를 유지하고, 외부 확장에 가변 `master`·최신 버전을 허용하지 않는다. 새 컴파일 키는 검토 후 별도 캐시로 확보하고 기존 키의 결과를 덮어쓰지 않는다.

### 9.4. BMP280 편입 조사 결과

**확인한 사실:** 현재 `public/firmware/bmp280-uart-v1.hex`를 고정 PXT 13.0.1의 `pxt.cpp.unpackSourceFromHexAsync`로 읽어 `main.ts`와 `pxt.json`을 확인했다. 원본 앱의 소스가 전혀 없는 상태는 아니다. 다만 HEX에는 외부 확장 구현 전체가 내장돼 있지 않으며, 원래 산출물을 같은 바이트로 재빌드한 것은 아니다.

- 내장 설정은 target **3.0.17 / PXT 6.0.18**이며, 현재 공통 빌드의 9.1.1 / 13.0.1과 다르다. 이 구버전 입력을 현재 캐시에 억지로 맞추지 않고 새 버전 후보로 이식한다.
- 실제 센서 호출은 `BME280.temperature`, `humidity`, `pressure`다. `BME280` 의존성은 `makecode-extensions/BME280_2`의 **`141a8f57653535b082926777c3ef79c8b7269964`**로 고정돼 있다. 해당 [pxt.json](https://github.com/makecode-extensions/BME280_2/blob/141a8f57653535b082926777c3ef79c8b7269964/pxt.json)은 core만 의존하고, 실행 코드는 [BME280.ts](https://github.com/makecode-extensions/BME280_2/blob/141a8f57653535b082926777c3ef79c8b7269964/BME280.ts)이다. 추가 네이티브 소스·설정 없이 기존 I²C/버퍼 API를 사용하며 [MIT 라이선스](https://github.com/makecode-extensions/BME280_2/blob/141a8f57653535b082926777c3ef79c8b7269964/LICENSE)를 확인했다.
- 원본 프로젝트에는 microphone·servo·환경 키트·SHT2x·sonar도 선언돼 있다. 읽은 `main.ts`에서 이들 센서 API 호출은 확인되지 않았다. 공통 런타임으로 그대로 옮기지 않고 제거 가능한지 후보 빌드와 동작 비교로 확인한다. 확장 최상위 초기화까지 살펴야 하므로 호출이 없다는 사실만으로 무영향을 단정하지 않는다.
- 드라이버는 최상위에서 I²C 보정 레지스터를 읽고 초기 설정을 쓴다. BMP280 프로그램에만 포함하고 다른 센서 프로그램의 시작 조건으로 만들지 않는다. 외장 장치가 없거나 응답하지 않을 때도 재설치·복구 경로가 막히지 않아야 한다.

**구현한 후보:** 원본 확장 전체를 가져오는 대신 Bosch 공식 보정식과 기존 I²C API로 `firmware/drivers/bmp280.ts`를 작성하고, 센서 실행 코드에서 사용한다. 추가 C++·외부 네이티브 캐시 없이 현재 시험 프로필로 빌드했으며 내장 센서들과 실제 런타임 바이트가 일치한다. 원본 BME280 확장과 기존 앱의 라이선스 기록은 조사 출처로 보존하고 새 드라이버에는 수학적 근거를 명시했다.

**계산식 확인·수정:** 기존 확장의 `(t * 5 + 128) >> 8 / 100`은 나눗셈이 먼저 계산돼 의도한 시프트가 되지 않는다. 원본 main의 `/256`·`/100`이 상당 부분 상쇄하므로 기존 자료 전체가 256배 틀렸다는 뜻은 아니다. PC의 합성 레지스터 사례에서 기존 경로는 25.09°C, 공식 부동소수점식은 약 25.08248°C였다. 새 후보는 °C를 직접 계산하고 이중 보정을 제거한다. 압력도 같은 온도 보정값을 쓰는 공식 부동소수점식으로 계산하며, 온도/압력 6바이트를 한 번에 읽어 시점 혼합을 막는다. 근거는 [Bosch BMP280 데이터시트](https://www.bosch-sensortec.com/media/boschsensortec/downloads/datasheets/bst-bmp280-ds001.pdf) §3.9·§8.1이다.

기존 `bme` 명령·3열·°C/hPa·명목 100 ms는 유지하며 습도 자리는 빈 값으로 보낸다. 장치 ID·부호 있는 보정 계수·초기화 대기·미지원 측정값을 검사하고 실패 시 `,,`로 보내 이전 값을 재사용하지 않는다. 새 후보는 firmware v2이며 앱은 v1을 계속 제공한다. 기존 저장 자료를 소급 재계산하지 않는다. [수치·통신 검사](../tests/unit/external-sensor-firmware.test.mjs)는 독립적인 Bosch 정수식으로 계산한 합성 입력 4개(음수/양수 온도 포함), 0x76/0x77, 일괄 읽기, 실패·중단/재연결을 검사한다. 이는 실제 보드의 연산·센서 정확도 검증을 대신하지 않는다.

### 9.5. 빌드·배포 계약

기존 `targets.json`, `pxt-template.json`, 빌드 기록·캐시·펌웨어 허용 목록을 확장한다. `additionalSources`로 로컬 JS/TS 소스를 명시하고 각 파일의 내장 내용·해시를 검사하며 다운로드용 소스를 합친다. 네이티브 의존성은 여전히 core + bluetooth로 제한한다. `trial-image.mjs`의 파일/메모리 검증을 기존 전송 산출물 생성과 `check-common-runtime.mjs`가 공유한다. 외부 확장 패키지를 임의 허용하는 범용 로더는 추가하지 않았다.

| 관리 대상 | 필요한 기록·검사 |
|---|---|
| 공통 런타임 프로필 | 계열 ID·도구/target/CODAL 버전·설정 해시·외부/전이 의존성 커밋과 내용 해시·라이선스·네이티브 compile key·원본 캐시 SHA-256 |
| V2 실행 영역 | 장치 조회용 런타임 식별값, 정규화한 메모리 영역의 SHA-256·시작/끝·프로그램 시작 주소·허용 상한. 캐시 HEX 텍스트 해시와 실행 영역 해시를 혼동하지 않음 |
| 센서별 산출물 | 센서 ID·펌웨어 버전·코덱·시작 명령·간격, 모든 입력 파일 해시, 내장 소스/설정 검증, USB용 전체 HEX와 그 HEX에서 추출한 부분 BIN·각 해시·영역·프로그램 식별값 |
| 공개 등록 | 기존 펌웨어 허용 목록이 설치 가능 파일의 단일 기준. 빌드 성공만으로 자동 배포하지 않음. 정적 호환과 실물 확인 환경을 따로 기록 |

같은 계열의 모든 후보는 네이티브 메모리 영역을 패딩 규칙까지 통일해 비교하고 **바이트 차이 0**, 런타임 식별값·프로그램 시작 주소 일치를 요구한다. TypeScript 전용 외장 드라이버와 기존 다중 채널 예제 `temperature-light`를 확장 회귀 사례로 사용한다. 예제가 빌드되더라도 앱 센서로 자동 등록하지 않는다. USB와 무선 파일을 따로 컴파일하지 않고 하나의 검증된 HEX에서 파생해 내용 차이를 막는다.

### 9.6. 호환 판정과 갱신 정책

무선 전송 허용 조건은 **지원 V2·서비스/모드 확인 ∧ 등록된 대상 파일 검증 ∧ 등록된 공통 런타임 식별 일치 ∧ 프로그램 시작 주소 일치 ∧ 전송 범위가 허용 영역 안에 있음**이다. 계열 이름·센서 이름·브라우저에 저장된 마지막 설치 기록으로 이 판정을 대신하지 않는다. [공식 부분 전송 구현의 런타임·주소 비교](https://github.com/microbit-foundation/microbit-connection/blob/12cbc608be4f5cfb0496b822ae6636389d8b97a4/packages/microbit-connection/src/bluetooth/flashing/flashing-partial.ts)

- 프로그램만 변경되고 위 조건이 유지되면 새 펌웨어 버전으로 무선 설치한다. 공통 네이티브 코드·보안 설정·영역이 바뀌면 새 런타임 계열을 발행하고 USB 설치를 안내한다. 런타임 식별값을 임의로 맞춰 호환 검사를 통과시키지 않는다.
- 공통 계열의 첫 정식 배포는 현재 다섯 센서를 함께 빌드·검증한 뒤 등록한다. 새 네이티브 기능의 도입도 해당 계열 전체를 함께 검증한다. 센서별 독립 런타임으로 갈라져 무선 전환이 끊기는 것을 기본 확장 방식으로 삼지 않는다.
- 이전 배포 파일·해시·과거 실험의 펌웨어 사본은 보존한다. 런타임 호환 여부와 기록 파일의 코덱/이어 측정 호환 여부는 별도 계약이다. 런타임이 같아도 채널·단위가 다르면 호환 측정으로 간주하지 않는다.
- 중단으로 프로그램 헤더가 손상되면 조회되는 해시도 신뢰할 수 없을 수 있다. 등록 런타임·영역을 확인할 수 없는 상태는 USB로 복구한다. 무선 재시도가 가능한 조건은 실물로 입증한 뒤 한정하며 검사 생략으로 복구하지 않는다.

장치가 보고하는 8바이트 식별값은 메모리의 표식에서 읽으며 실제 전체 플래시를 다시 해시한 결과가 아니다. 파일 SHA-256·블록 ACK·종료 요청·재연결 식별·새 수신을 각각 기록하고 설치 완료 판단에 사용하되, 장치 측 암호학적 전체 이미지 검증으로 표현하지 않는다. [CODAL의 식별값 조회](https://github.com/lancaster-university/codal-microbit-v2/blob/f5d1682fc3882022d3d5a7facb1fddb4b0ea7b52/source/MicroBitMemoryMap.cpp)

### 9.7. 자원·복구 검증과 다음 산출물

현재 시험본의 프로그램 영역은 `0x49000–0x73000`으로 168 KiB지만 향후 모든 런타임의 고정 주소·용량으로 일반화하지 않는다. 프로필별 실제 맵에서 시작/끝·패딩·남은 공간을 검사하고 SoftDevice·부트로더·예약 영역으로 쓰지 못하게 한다. 네이티브 기능을 추가할 때는 플래시 증가뿐 아니라 정적 RAM·힙/스택 여유·GATT 사용량과 최대 메시지/센서 버퍼를 기록한다. API 호출 가능성만으로 자원 여유를 판단하지 않는다.

부분 전송은 플래시 페이지를 지우고 쓰며 중단 시 이전 프로그램 보존을 보장하지 않는다. 긴 프로그램→짧은 프로그램, 페이지/64바이트 경계, 프로그램 끝의 남은 페이지 처리, 첫·중간·마지막 전송에서의 단절/전원 차단을 확인한다. CODAL의 완료 처리는 보드 사용자 저장소도 지우므로 보드에 보정값·설정을 영구 보관하는 확장에는 별도 정책이 필요하다. 앱 DB의 저장 자료 보존과 혼동하지 않는다. [CODAL 부분 전송·완료 처리](https://github.com/lancaster-university/codal-microbit-v2/blob/f5d1682fc3882022d3d5a7facb1fddb4b0ea7b52/source/bluetooth/MicroBitPartialFlashingService.cpp)

**구현 상태:** 후보 7개는 같은 런타임·시작 주소·네이티브 바이트로 빌드됐고 개발 전송 목록에 등록했다. BMP280 교체 자료는 8,320 B, 아날로그는 4,480 B다. 명령·해시는 [빌드 안내](../dev/firmware/README.md), 시험 방법은 [시험실 안내](../dev/bluetooth-install/README.md#빠른-시험과-로컬-명령), 실물 결과와 다음 작업은 [§8.4](#84-현재-검증-결과와-남은-작업)를 따른다. cppDependencies는 필요한 네이티브 확장이 생길 때 검토한다.


### 9.8. 아날로그 센서 기반

사용자 요청으로 아날로그 입력을 M6 공통 런타임 검증 대상에 포함했다. 현재 `analog-raw`는 P0/P1/P2를 순서대로 읽어 3열 원시 ADC 값(0–1023)을 명목 100 ms마다 송신하는 개발용 시험 기반이다. `start`/`stop`과 연결 해제 후 새 시작 계약을 유지하고 0·1023을 결측으로 취급하지 않는다. [MakeCode 아날로그 입력 규약](https://makecode.microbit.org/reference/pins/analog-read-pin)

ADC 값과 전압·온도·힘 등 물리량은 구분한다. 센서별 핀·범위·변환식·기준 전압/보정 조건은 해당 센서 정의와 드라이버에서 관리하며 공통 런타임에 고정 환산식을 넣지 않는다. 현재 기반에는 자동 평활화·백분율 정규화·사용자 편집 수식·센서 카탈로그 UI를 추가하지 않았다. 특정 아날로그 센서의 앱 등록·준비 안내·코덱·자료 보존은 실제 대상과 사용 흐름을 정한 뒤 연결한다.

정적/모의 확인은 세 채널 순서·0/중간/최대 입력·시작/중단·재연결과 기존 런타임 일치까지다. 실물은 센서 미연결 원시값 수신을 확인했다. 후속 실물 검증에서는 세 핀 각각의 기준 입력·중간 전압·부유 입력·배선 분리, 순차 읽기와 실제 수신 간격, Bluetooth/다른 핀 기능 공존을 확인한다. 원시값이 들어온다는 이유만으로 연결된 센서 종류나 물리량 정확성을 자동 판정하지 않는다.
