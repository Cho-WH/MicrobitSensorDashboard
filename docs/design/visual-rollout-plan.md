# Luminous Lab 단계별 적용 설계

> **v2 — 전체 화면 검증 후 공통화**  
> 대상: `Cho-WH/MicrobitSensorDashboard`  
> 소스 검토 기준: `791d792c543ada0d0f9064b1067031c527b622b1` · v1 작성 시 확인한 소스  
> 디자인 기준: [시각 디자인 문법](visual-language.md) · 대화에서 선택한 기준 시안(원본 이미지 별도 보관; 저장소에 미포함)  
> 범위: 디자인 우선 개편. 필요한 UI 재배치·재구성 포함, 기능·과학적 의미·데이터 보존.  
> 상태: 2026-10-25 문서 개정. 앱 구현·저장소 변경·브라우저 검증은 아직 수행하지 않음.

## 1. 목표와 진행 순서

**선택한 시안의 창의적이고 세련되며 차분한 미래적 인상을 실제 앱에 구현한다.** 기존 UI 구조를 보존하는 것이 목표가 아니다. 기능 기획을 무작정 늘리기보다 전체 화면의 비례·재질·빛·서체·조작부 완성도를 우선한다.

진행 순서는 다음과 같다. 기능 개발의 M1/M2/M3와 구분해 디자인 단계는 V0–V5를 사용한다.

| 단계 | 중심 작업 | 단계의 결과 |
|---|---|---|
| V0 | 기존 기능·상태 확인, 시안 해석, 기준 캡처 | 전체 화면을 설계할 출발점과 임시 디자인 값 |
| V1 | 실제 측정 화면 전체 시안 제작·작동 검토·수정, 준비 대표 장면 검토 | 사용자와 검토할 수 있는 작동하는 기준 화면과 장면 |
| V2 | 검증한 표현을 토큰·부품·차트 테마로 공통화 | 다른 화면에서 재사용할 최소한의 구현 문법 |
| V3 | 준비 장면과 안내 전체에 적용 | 장비 연출과 실제 준비 기능이 연결된 화면 |
| V4 | 분석·해석·홈·저장·출력으로 확장 | 실제 사용 경로 전체의 일관된 디자인 |
| V5 | 주요 상태·반응형·접근성·성능 확인과 정리 | 기본 적용 가능한 새 디자인 |

**임시 규칙 → 전체 화면 구현·검토 → 공통 규칙 확정 → 확장** 순서다. V1에서도 토큰과 기존 공통 부품을 사용할 수 있지만, 실제 화면을 보기 전에 범용 디자인 시스템을 확정하지 않는다. 부품 표본은 전체 화면을 보조하는 검토 도구다.

개발 브랜치 또는 개발용 테마 선택 경로에서 작업한다. `data-visual-theme="luminous"`는 가능한 방법이며 필수 구조는 아니다. 검토 중인 시안을 운영 기본값으로 바로 바꾸지 않는다. 단계별 변경과 되돌리기 범위가 드러나도록 커밋한다.

## 2. 변경 권한과 보존할 계약

### 2.1. 디자인 목표에 맞게 조정할 수 있는 것

| 대상 | 허용되는 조정 | 함께 살필 점 |
|---|---|---|
| 전체 레이아웃 | 영역 재배치, 폭·높이·여백, 열 구성, 반응형 재구성 | 실제 문구·채널 수·화면 크기에서의 균형 |
| 탐색 | 상단·사이드바·혼합 배치, 단계 표시의 형태와 위치 | 현재 작업 위치와 각 기능에 대한 접근성 |
| 조작부 | 버튼 형태, 도구 묶음, 이동, 접기·펼치기, 상황별 노출 | 필요한 행동을 찾을 수 있는지, 현재 상태가 보이는지 |
| 정보 표시 | 계기 그룹, 범례, 상태·사건·메모의 재표현 | 연결·기록·저장의 구별, 기존 자료와의 정확한 연결 |
| 준비 장면 | 카메라·조명·재질·배경·장비 구도, 전체 어두운 연출, 시각 자산 보강 | 단자·배선·장비의 정확성, 안내의 읽기성 |
| 마크업·스타일 | 의미 있는 묶음과 DOM 구조, 클래스, 스타일 소유권 정리 | 이벤트 연결, 키보드 이동, 차트 크기, 뷰어 수명 |

이동·접기·노출 방식 변경을 이유만으로 범위 밖으로 밀어내지 않는다. 사용 경험에 미치는 영향과 필요한 이유를 시안 검토에 포함한다. 기존 상단 탐색이나 도구 위치를 고정하지도, 시안의 사이드바를 무조건 채택하지도 않는다.

### 2.2. 보존할 것과 따로 판단할 것

원자료, 단위·정밀도, 기록 수명, 연결·보정·수신 판단, 저장·복원, 분석 범위·선택·제외의 의미, 파일·프로토콜 호환성은 보존한다. 화면을 이동하거나 재배치했다고 기록이 초기화되거나 장치 연결이 끊겨서는 안 된다.

기능에 접근하는 방법은 재설계할 수 있다. 반면 기능 삭제, 실험 절차 변경, 새 수집·저장·분석 기능은 필요한지와 영향을 따로 판단한다. 기존 자료로 작은 추이선을 보여주거나 기존 사건을 다른 형식으로 표시하는 것과 새 기능 엔진을 추가하는 것을 구분한다.

DOM ID·`data-view` 같은 이름은 기존 이벤트 연결을 조사해 유지하거나, 변경 시 호출부·접근성 관계·관련 검사를 함께 갱신한다. 문자열이나 기존 DOM 위치 자체를 디자인 제약으로 삼지 않는다. 실험 상태의 작성자와 공통 모듈의 책임은 유지한다. [R1, R2]

## 3. V0 — 출발점과 전체 화면 설계

**목표:** 기존 앱의 실제 기능을 파악하고 시안에서 재현할 시각적 특징을 정한다.

**작업:**

- 작업 시작 시 최신 커밋·작업 트리와 문서의 소스 검토 기준 사이 변경을 확인한다. 진행 중인 다른 작업을 보존한다.
- 실제 측정 화면의 정상·기록 중·일시정지·수신 끊김을 확인하고 기준 캡처를 남긴다. 준비·분석은 변경 영향을 판단할 정도로 살핀다.
- 비교의 1차 기준은 1366×768의 BMP280 2채널 측정 화면으로 삼는다. 자료·시각·기록 상태를 통제하고, 모의 장치를 사용한 화면임을 개발 검토 자료에 표시한다.
- 시안의 해당 화면과 현재 앱을 비교해 전체 비례, 정보 밀도, 표면 깊이, 글자, 조작부, 장면의 차이를 정리한다. 같은 배치를 유지할 필요는 없다.
- 새 배치와 각 영역의 시각적 역할을 잡고 임시 토큰으로 전체 화면 시안을 시작한다. 차이가 큰 구도는 가볍게 비교할 수 있으나 여러 대안 제작 자체를 필수 절차로 만들지 않는다.

**산출물:** 기존 캡처, 시안에서 이어갈 특징과 조정할 항목, 첫 전체 화면 구성. 별도의 긴 기획 문서를 추가하는 대신 실제 화면에서 사용할 판단만 남긴다.

**완료 기준:** 기능·데이터를 보존하면서 무엇을 시각적으로 바꿀지 설명할 수 있고, V1의 실제 화면 구현으로 이어진다. 버튼 표본 제작을 V0의 최종 목표로 삼지 않는다.

## 4. V1 — 작동하는 측정 기준 화면과 준비 장면

### 4.1. 측정 화면 전체를 먼저 완성

**목표:** 시안의 인상이 기존 앱의 실제 기능·한글 문구·자료와 함께 성립하는지 확인한다.

- 기존 앱의 실제 측정 경로를 개발용으로 새로 표현한다. 기존 mock·연결 상태·기록 제어·차트·메모 경로를 재사용한다. 독립적인 가짜 앱을 만들고 나중에 기능을 이식하는 방식을 기본으로 삼지 않는다.
- 탐색·헤더·장치 상태·계기·기록 제어·그래프·메모의 배치와 묶음을 조정한다. 전체 비례와 정보 밀도를 먼저 맞춘 뒤 표면·글자·아이콘·미세 간격을 다듬는다.
- 실제 한국어 라벨, 지원 채널, 단위, 큰 값·음수·값 없음 상태를 넣는다. 시안의 허구 숫자나 연결 상태를 운영 UI에 고정하지 않는다.
- CSS와 차트의 표현을 함께 바꾼다. 화면은 새로워졌지만 그래프에 이전 테마만 남는 상태를 해결한다. 임시 토큰과 작은 표시 어댑터를 사용할 수 있다.
- 기록 전/기록 중/일시정지/수신 끊김의 실제 상태에서 조작과 화면 변화를 확인한다. 저장 실패는 검증 가능한 기존 경로나 통제된 시험으로 별도 확인하고, 시험 상태와 실제 장치 검증을 구별한다.
- 대표 화면이 잡히면 1024px 너비와 작은 화면에서 재배치 가능성을 확인한다. 핵심 글자·버튼을 축소하거나 숨겨 공간을 억지로 맞추지 않는다.

시각 검토용 고정 데이터를 쓸 수 있지만 기록·표시 경로는 실제 앱을 사용한다. 아직 연결하지 않은 동작이 있다면 명시하고, 해당 부분을 작동 검증 완료로 보고하지 않는다. 전체 화면 기준을 확정할 때에는 관련 주요 조작이 실제 경로로 이어져야 한다.

### 4.2. 준비 장면 한 컷을 별도로 확인

준비 화면의 미래적인 장면은 공통 버튼·색만으로 검증되지 않는다. 기존 자산의 지원 범위를 확인해 **장비·구도·빛·배경·전후 겹침**이 함께 있는 대표 장면을 만든다.

기존 3D 모델·배선 자료를 재사용하되 카메라·조명·배경을 바꿀 수 있다. 추가 정적 렌더나 분위기 자산이 더 적합하면 활용한다. 그림 영역만 어둡게 하는 방식과 준비 작업 화면 전체를 어둡게 하는 방식은 실제 시안의 결과로 판단한다.

이 단계에서는 대표 장면과 안내를 포함한 한 컷으로 표현 가능성을 검토한다. 모든 준비 단계와 연결하는 작업은 V3에서 한다. 단순 배경색 변경만으로 장면이 검증되었다고 처리하지 않는다. 새 자산의 용도·출처와 하드웨어 정확성 확인 범위를 남긴다.

### 4.3. 비교·수정·기준 확정

검토 순서는 **전체 비례·위계 → 표면·빛·색 → 서체·정렬·아이콘 → 상태·반응형 세부**를 기본으로 한다. 앞 단계의 문제가 크면 토큰이나 배치까지 다시 조정한다.

사용자에게 실제 브라우저의 전체 화면과 주요 상태 캡처를 보여주고, 남은 차이를 관찰 가능한 말로 정리한다. 예: ‘상단 조작부가 무거워 그래프가 작아 보임’, ‘경계가 진해 떠 있는 표면보다 카드 목록처럼 보임’. 주관적인 점수만으로 완성도를 판정하지 않는다.

**산출물:** 작동하는 측정 화면, 대표 상태 캡처, 준비 장면 한 컷, 검토 후 남은 차이와 결정. 시안 이미지나 작은 부품 표본만을 산출물로 제출하지 않는다.

**완료 기준:** 사용자가 실제 시안을 보며 방향을 검토할 수 있고, 전체 인상과 관련 주요 조작을 확인한 화면이 공통화의 기준으로 정리된다. 남은 부분은 검증 완료 부분과 구분한다. 검토 전 임시 표현을 모든 화면으로 확산시키지 않는다.

**되돌리기:** 개발 브랜치/테마 적용과 해당 화면·차트 변경을 한 논리적 범위로 되돌릴 수 있게 한다. 원자료나 저장 파일에는 시각 변경을 위한 마이그레이션을 만들지 않는다.

## 5. V2 — 검증한 표현을 공통화

**목표:** V1의 완성된 화면에서 다른 화면에도 필요한 규칙과 부품을 추출한다.

- 실제로 사용한 색·모서리·그림자·서체·간격·모션을 공통 토큰으로 정리한다. 초기값을 지키기 위해 검토된 화면을 되돌리지 않는다.
- 버튼·입력·상태·계기·탭 등 반복되는 표현과 기본/호버/누름/초점/비활성/진행 상태를 정리한다. 한 번 쓰이는 장면까지 범용 부품으로 추상화하지 않는다.
- DOM과 Canvas가 같은 색·글자·분석 상태 규칙을 사용하도록 작은 표시 모듈을 정리한다. V1에서 만든 연결 코드가 충분하면 확장하지 않는다.
- 필요하면 실제 사용 부품을 가져오는 작은 개발용 표본을 둔다. 앱과 별도의 복제 부품·독립 상태 로직을 유지하지 않는다.
- 시각 문법 문서와 대비 기록을 실제 채택값으로 갱신한다. 폰트·아이콘·자산의 출처와 라이선스를 보존한다.

**완료 기준:** 기준 화면의 인상을 유지한 채 공통 표현을 재사용할 수 있다. 토큰 선언만 있거나, 공통화 후 실제 화면의 비례가 달라지는 상태는 완료가 아니다.

### 5.1. CSS·Canvas 구현 원칙

스타일은 책임을 가진 기존 파일부터 정리한다. `--teal`을 한 색으로 일괄 치환하지 않고 행동·선택·자료·상태 토큰을 구분한다. 필요 없는 우선순위 경쟁이나 `!important` 덮어쓰기를 누적하지 않는다.

기존 비계층 CSS를 둔 채 새 CSS만 `@layer`에 넣으면 로딩 순서만으로 우선순위가 해결된다고 가정하지 않는다. 현행 캐스케이드에 맞게 적용하며, 계층 개편이 필요하면 영향 범위를 함께 확인한다. [W5]

`visual-theme.js`는 뷰 초기화·테마 적용 시 CSS 토큰을 읽고, 채널·분석 상태의 표시값을 해석해 화면과 PNG 생성에 전달하는 정도로 시작한다. 매 샘플마다 스타일을 다시 읽지 않는다. 저장된 정의 사본의 오래된 색과 새 테마의 우선순위를 표시 계층에서 처리한다. 단위·정밀도·원자료를 테마 객체에 복제하거나 저장 파일을 수정하지 않는다.

## 6. V3 — 준비 화면 전체 적용

**목표:** V1에서 확인한 장면을 실제 준비 안내와 연결한다.

- 검토한 카메라·조명·구도·표면을 바탕으로 준비 화면을 설계한다. 안내·단계·버튼의 위치도 장면과 함께 조정한다.
- 정확한 배선·USB·보정·수신 안내가 실제 상태를 반영하게 한다. 분위기 장면과 자세한 배선 확인의 역할을 분리할 수 있다.
- 내장 센서·BMP280·게이뤼삭의 차이를 기존 모듈에서 반영한다. 모든 센서를 같은 하드웨어 그림으로 표현하지 않는다.
- 단계 이동, 도움말, 키보드 초점, 화면 크기 변경을 확인한다. 뷰어 재생성·초기화 깜빡임·상태 손실을 막는다.
- 정적 자산과 실제 조작이 필요한 3D의 역할을 나누고 로딩·성능을 살핀다. 기존 자산만 고수해 완성도를 낮추지도, 분위기만을 위해 새 렌더링 엔진을 먼저 도입하지도 않는다.

**완료 기준:** 남색 배경을 추가한 수준이 아니라 장비 장면과 안내의 완성도가 함께 확보된다. 큰 화면과 작은 화면 모두 준비 행동을 수행할 수 있다.

**검증:** 변경한 준비 단계·단계 전환·도움말·뷰어 수명·가독성. 외형 검토를 실물 하드웨어 검증으로 보고하지 않는다.

## 7. V4 — 분석·해석·홈·저장·출력 확장

**목표:** 기준 화면에서 검증한 문법을 각 화면의 실제 작업에 맞게 적용한다.

- 분석 화면의 표·그래프·도구·탭을 필요에 따라 재배치한다. 자료의 선택/적용, 포함/제외, 추세선·연장선의 의미는 보존한다.
- 결과 해석의 글자·입력·근거 표시를 정리한다. 학습 문항과 판단의 의미를 시각 변경 때문에 바꾸지 않는다.
- 홈·저장 목록은 센서/활동 선택, 기존 실험 이어하기, 파일 접근을 제공하면서 배치와 표현을 재설계할 수 있다.
- 도움말·팝오버·모달·오류·빈 상태까지 표현을 연결한다. 보기 좋은 정상 상태만 새 테마로 남기지 않는다.
- 화면 밖에서 생성하는 분석 PNG에도 같은 글자·채널·포함/제외·추세선 규칙을 적용한다. 출력은 명료한 흰 자료 바탕으로 만들고 장식용 앱 배경은 제외한다.

**완료 기준:** 준비→측정→분석→저장의 실제 흐름에서 디자인이 일관되고, 과거 실험을 열어도 표현이 섞이지 않는다. 모든 화면을 같은 카드 격자로 만들 필요는 없다.

**검증:** 변경한 탐색과 조작, 구간 선택·적용, 제외/복원, 보기 전환, 되돌리기, 해석 보존, PNG, JSON/CSV의 내용 보존. 공통 차트 변경이 영향을 주는 경로를 함께 검사한다.

## 8. V5 — 통합 검토와 기본 적용

- 기준 화면과 확장 화면의 실제 캡처를 비교한다. 전체 비례·시각적 위계·장면의 품질·상태 표현이 함께 유지되는지 확인한다.
- 대비·키보드 초점·200% 글자 확대·작은 화면·모션 감소·필터 없음·폰트 로딩 실패를 확인한다. 선명한 디자인을 위해 글자를 줄이는 식의 우회를 정리한다.
- 같은 모의 자료와 같은 환경으로 값 갱신·차트·표 스크롤·뷰 전환을 비교한다. 기준 캡처만으로 성능이나 하드웨어 동작이 검증되었다고 추정하지 않는다.
- 이전 하드코딩 색·중복 선언·사용하지 않는 토큰·임시 비교 코드를 정리한다. 보존할 작은 개발 표본은 실제 부품을 사용하도록 유지한다.
- 검토를 마친 뒤 새 디자인을 기본 적용하고 문서·외부 자산 고지·시각 기준 캡처를 채택 결과에 맞춘다. 사용자용 테마 설정을 만들 필요가 없다면 개발용 전환 장치는 정리한다.

**완료 기준:** 시각 검토와 대표 기능·상태·출력 검토를 구분해 마친다. 미확인 환경은 남긴다. 모든 환경을 검증했다고 일반화하지 않는다.

**검사 전략:** 단계별 변경 영향부터 검사한다. 공통 UI·차트·탐색을 폭넓게 바꿨다면 관련 경로를 확장하고, 최종 통합 시 필요한 `npm run typecheck`, `npm test`, `npm run build` 및 브라우저 검사를 묶어 수행한다. 같은 상태의 전체 검사를 반복하지 않는다. 문서 개정만 한 작업을 앱 검사 완료로 보고하지 않는다.

## 10. 대표 검토 범위

모든 조합을 곱집합으로 검사하지 않는다. 공통 부품 상태는 작은 표본으로, 화면 비례와 동작은 실제 사용 경로로 확인한다.

| 경로 | 주요 확인 | 대표 화면 크기 |
|---|---|---|
| 측정 기준 | BMP280 2채널, 기록 전·기록 중·일시정지·수신 끊김 | 1366×768, 1024×768 |
| 측정 확장 | 1채널·벡터 다채널, 큰 값·음수·긴 단위·값 없음 | 1366×768, 390×844 |
| 준비 | 대표 장면, 배선/USB·내장 센서·보정, 단계 이동·뷰어 수명 | 1366×768, 768×1024 |
| 분석 | 표/그래프, 구간 선택·적용, 포함/제외·추세선·PNG | 1366×768, 1024×768 및 출력 |
| 해석·저장·오류 | 긴 한국어, 빈 상태, 저장 실패, 파일 오류 | 1366×768, 390×844 |
| 접근성·동작 | 초점·읽기 순서·200% 확대·320px 재배치·모션 감소 | 영향받은 대표 화면 |

화면 크기는 출발점이며 실제 사용 환경에 따라 조정한다. 표처럼 2차원 구조가 필요한 영역은 명시적인 내부 스크롤을 검토한다. 작은 화면의 문제를 무조건 폰트 축소로 해결하지 않는다.

## 11. 검토 자료와 결정 기록

기준 시안의 해당 화면과 실제 앱의 전체 캡처를 비교한다. 같은 자료·상태·뷰포트를 사용하되 기존 배치를 유지할 필요는 없다. 장식용 랜딩 화면만으로 새 디자인을 완료 판정하지 않는다.

각 검토에는 다음 내용만 짧게 남긴다.

```text
단계/소스: V1, 작업 커밋 또는 브랜치 ...

시각 변경: 영역 비례·묶음·빛·서체 등 ...
보존한 동작 / 아직 연결하지 않은 동작: ...
검사 결과 / 미확인 환경: ...
남은 시각 차이와 다음 수정: ...
검토 결정: 유지할 표현 / 수정할 표현 / 공통화할 표현 ...
```

‘문서 준수’, ‘토큰 구현’, ‘테스트 통과’와 ‘시각적 완성도 확인’을 구분한다. 화면이 충분히 좋아지지 않았다면 기존 치수나 배치를 지킨 사실로 완료를 대신하지 않는다.
