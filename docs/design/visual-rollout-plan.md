## 1. 목표와 진행 순서

**선택한 시안의 창의적이고 세련되며 차분한 미래적 인상을 실제 앱에 구현한다.** 기존 UI 구조를 보존하는 것이 목표가 아니다. 기능 기획을 무작정 늘리기보다 전체 화면의 비례·재질·빛·서체·조작부 완성도를 우선한다.

진행 순서는 다음과 같다. 기능 개발의 M1/M2/M3와 구분해 디자인 단계는 V0–V5를 사용한다.

| 단계 | 중심 작업 | 단계의 결과 |
|---|---|---|
| V0 | 기존 기능·상태 확인, 시안 해석, 기준 캡처 | 전체 화면을 설계할 출발점과 임시 디자인 값 |
| V1 | 실제 측정 화면 전체 시안 제작·작동 검토·수정, 준비 대표 장면 검토 | 사용자와 검토할 수 있는 작동하는 기준 화면과 장면 |
| V2 | 검증한 표현을 토큰·부품·차트 테마로 공통화 | 다른 화면에서 재사용할 최소한의 구현 문법 |
| V3 | 준비 장면과 안내 전체에 적용 | 장비 연출과 실제 준비 기능이 연결된 화면 |
| V4 | 분석·해석·홈·저장·출력으로 확장 | 실제 사용 경로 전체의 일관된 디자인 |
| V5 | 주요 상태·반응형·접근성·성능 확인과 정리 | 기본 적용 가능한 새 디자인 |

**임시 규칙 → 전체 화면 구현·검토 → 공통 규칙 확정 → 확장** 순서다. V1에서도 토큰과 기존 공통 부품을 사용할 수 있지만, 실제 화면을 보기 전에 범용 디자인 시스템을 확정하지 않는다. 부품 표본은 전체 화면을 보조하는 검토 도구다.

개발 브랜치 또는 개발용 테마 선택 경로에서 작업한다. `data-visual-theme="luminous"`는 가능한 방법이며 필수 구조는 아니다. 검토 중인 시안을 운영 기본값으로 바로 바꾸지 않는다. 단계별 변경과 되돌리기 범위가 드러나도록 커밋한다.

## 2. 변경 권한과 보존할 계약

### 2.1. 디자인 목표에 맞게 조정할 수 있는 것

| 대상 | 허용되는 조정 | 함께 살필 점 |
|---|---|---|
| 전체 레이아웃 | 영역 재배치, 폭·높이·여백, 열 구성, 반응형 재구성 | 실제 문구·채널 수·화면 크기에서의 균형 |
| 탐색 | 상단·사이드바·혼합 배치, 단계 표시의 형태와 위치 | 현재 작업 위치와 각 기능에 대한 접근성 |
| 조작부 | 버튼 형태, 도구 묶음, 이동, 접기·펼치기, 상황별 노출 | 필요한 행동을 찾을 수 있는지, 현재 상태가 보이는지 |
| 정보 표시 | 계기 그룹, 범례, 상태·사건·메모의 재표현 | 연결·기록·저장의 구별, 기존 자료와의 정확한 연결 |
| 준비 장면 | 카메라·조명·재질·배경·장비 구도, 전체 어두운 연출, 시각 자산 보강 | 단자·배선·장비의 정확성, 안내의 읽기성 |
| 마크업·스타일 | 의미 있는 묶음과 DOM 구조, 클래스, 스타일 소유권 정리 | 이벤트 연결, 키보드 이동, 차트 크기, 뷰어 수명 |

이동·접기·노출 방식 변경을 이유만으로 범위 밖으로 밀어내지 않는다. 사용 경험에 미치는 영향과 필요한 이유를 시안 검토에 포함한다. 기존 상단 탐색이나 도구 위치를 고정하지도, 시안의 사이드바를 무조건 채택하지도 않는다.

### 2.2. 보존할 것과 따로 판단할 것

원자료, 단위·정밀도, 기록 수명, 연결·보정·수신 판단, 저장·복원, 분석 범위·선택·제외의 의미, 파일·프로토콜 호환성은 보존한다. 화면을 이동하거나 재배치했다고 기록이 초기화되거나 장치 연결이 끊겨서는 안 된다.

기능에 접근하는 방법은 재설계할 수 있다. 반면 기능 삭제, 실험 절차 변경, 새 수집·저장·분석 기능은 필요한지와 영향을 따로 판단한다. 기존 자료로 작은 추이선을 보여주거나 기존 사건을 다른 형식으로 표시하는 것과 새 기능 엔진을 추가하는 것을 구분한다.

DOM ID·`data-view` 같은 이름은 기존 이벤트 연결을 조사해 유지하거나, 변경 시 호출부·접근성 관계·관련 검사를 함께 갱신한다. 문자열이나 기존 DOM 위치 자체를 디자인 제약으로 삼지 않는다. 실험 상태의 작성자와 공통 모듈의 책임은 유지한다. [R1, R2]

## 3. V0 — 출발점과 전체 화면 설계

**목표:** 기존 앱의 실제 기능을 파악하고 시안에서 재현할 시각적 특징을 정한다.

**작업:**

- 작업 시작 시 최신 커밋·작업 트리와 문서의 소스 검토 기준 사이 변경을 확인한다. 진행 중인 다른 작업을 보존한다.
- 실제 측정 화면의 정상·기록 중·일시정지·수신 끊김을 확인하고 기준 캡처를 남긴다. 준비·분석은 변경 영향을 판단할 정도로 살핀다.
- 비교의 1차 기준은 1366×768의 BMP280 2채널 측정 화면으로 삼는다. 자료·시각·기록 상태를 통제하고, 모의 장치를 사용한 화면임을 개발 검토 자료에 표시한다.
- 시안의 해당 화면과 현재 앱을 비교해 전체 비례, 정보 밀도, 표면 깊이, 글자, 조작부, 장면의 차이를 정리한다. 같은 배치를 유지할 필요는 없다.
- 새 배치와 각 영역의 시각적 역할을 잡고 임시 토큰으로 전체 화면 시안을 시작한다. 차이가 큰 구도는 가볍게 비교할 수 있으나 여러 대안 제작 자체를 필수 절차로 만들지 않는다.

**산출물:** 기존 캡처, 시안에서 이어갈 특징과 조정할 항목, 첫 전체 화면 구성. 별도의 긴 기획 문서를 추가하는 대신 실제 화면에서 사용할 판단만 남긴다.

**완료 기준:** 기능·데이터를 보존하면서 무엇을 시각적으로 바꿀지 설명할 수 있고, V1의 실제 화면 구현으로 이어진다. 버튼 표본 제작을 V0의 최종 목표로 삼지 않는다.

## 4. V1 — 작동하는 측정 기준 화면과 준비 장면

### 4.1. 측정 화면 전체를 먼저 완성

**목표:** 시안의 인상이 기존 앱의 실제 기능·한글 문구·자료와 함께 성립하는지 확인한다.

- 기존 앱의 실제 측정 경로를 개발용으로 새로 표현한다. 기존 mock·연결 상태·기록 제어·차트·메모 경로를 재사용한다. 독립적인 가짜 앱을 만들고 나중에 기능을 이식하는 방식을 기본으로 삼지 않는다.
- 탐색·헤더·장치 상태·계기·기록 제어·그래프·메모의 배치와 묶음을 조정한다. 전체 비례와 정보 밀도를 먼저 맞춘 뒤 표면·글자·아이콘·미세 간격을 다듬는다.
- 실제 한국어 라벨, 지원 채널, 단위, 큰 값·음수·값 없음 상태를 넣는다. 시안의 허구 숫자나 연결 상태를 운영 UI에 고정하지 않는다.
- CSS와 차트의 표현을 함께 바꾼다. 화면은 새로워졌지만 그래프에 이전 테마만 남는 상태를 해결한다. 임시 토큰과 작은 표시 어댑터를 사용할 수 있다.
- 기록 전/기록 중/일시정지/수신 끊김의 실제 상태에서 조작과 화면 변화를 확인한다. 저장 실패는 검증 가능한 기존 경로나 통제된 시험으로 별도 확인하고, 시험 상태와 실제 장치 검증을 구별한다.
- 대표 화면이 잡히면 1024px 너비와 작은 화면에서 재배치 가능성을 확인한다. 핵심 글자·버튼을 축소하거나 숨겨 공간을 억지로 맞추지 않는다.

시각 검토용 고정 데이터를 쓸 수 있지만 기록·표시 경로는 실제 앱을 사용한다. 아직 연결하지 않은 동작이 있다면 명시하고, 해당 부분을 작동 검증 완료로 보고하지 않는다. 전체 화면 기준을 확정할 때에는 관련 주요 조작이 실제 경로로 이어져야 한다.

### 4.2. 준비 장면 한 컷을 별도로 확인

준비 화면의 미래적인 장면은 공통 버튼·색만으로 검증되지 않는다. 기존 자산의 지원 범위를 확인해 **장비·구도·빛·배경·전후 겹침**이 함께 있는 대표 장면을 만든다.

기존 3D 모델·배선 자료를 재사용하되 카메라·조명·배경을 바꿀 수 있다. 추가 정적 렌더나 분위기 자산이 더 적합하면 활용한다. 그림 영역만 어둡게 하는 방식과 준비 작업 화면 전체를 어둡게 하는 방식은 실제 시안의 결과로 판단한다.

이 단계에서는 대표 장면과 안내를 포함한 한 컷으로 표현 가능성을 검토한다. 모든 준비 단계와 연결하는 작업은 V3에서 한다. 단순 배경색 변경만으로 장면이 검증되었다고 처리하지 않는다. 새 자산의 용도·출처와 하드웨어 정확성 확인 범위를 남긴다.

### 4.3. 비교·수정·기준 확정

검토 순서는 **전체 비례·위계 → 표면·빛·색 → 서체·정렬·아이콘 → 상태·반응형 세부**를 기본으로 한다. 앞 단계의 문제가 크면 토큰이나 배치까지 다시 조정한다.

사용자에게 실제 브라우저의 전체 화면과 주요 상태 캡처를 보여주고, 남은 차이를 관찰 가능한 말로 정리한다. 예: ‘상단 조작부가 무거워 그래프가 작아 보임’, ‘경계가 진해 떠 있는 표면보다 카드 목록처럼 보임’. 주관적인 점수만으로 완성도를 판정하지 않는다.

**산출물:** 작동하는 측정 화면, 대표 상태 캡처, 준비 장면 한 컷, 검토 후 남은 차이와 결정. 시안 이미지나 작은 부품 표본만을 산출물로 제출하지 않는다.

**완료 기준:** 사용자가 실제 시안을 보며 방향을 검토할 수 있고, 전체 인상과 관련 주요 조작을 확인한 화면이 공통화의 기준으로 정리된다. 남은 부분은 검증 완료 부분과 구분한다. 검토 전 임시 표현을 모든 화면으로 확산시키지 않는다.

**되돌리기:** 개발 브랜치/테마 적용과 해당 화면·차트 변경을 한 논리적 범위로 되돌릴 수 있게 한다. 원자료나 저장 파일에는 시각 변경을 위한 마이그레이션을 만들지 않는다.

## 5. V2 — 검증한 표현을 공통화

**목표:** V1의 완성된 화면에서 다른 화면에도 필요한 규칙과 부품을 추출한다.

- 실제로 사용한 색·모서리·그림자·서체·간격·모션을 공통 토큰으로 정리한다. 초기값을 지키기 위해 검토된 화면을 되돌리지 않는다.
- 버튼·입력·상태·계기·탭 등 반복되는 표현과 기본/호버/누름/초점/비활성/진행 상태를 정리한다. 한 번 쓰이는 장면까지 범용 부품으로 추상화하지 않는다.
- DOM과 Canvas가 같은 색·글자·분석 상태 규칙을 사용하도록 작은 표시 모듈을 정리한다. V1에서 만든 연결 코드가 충분하면 확장하지 않는다.
- 필요하면 실제 사용 부품을 가져오는 작은 개발용 표본을 둔다. 앱과 별도의 복제 부품·독립 상태 로직을 유지하지 않는다.
- 시각 문법 문서와 대비 기록을 실제 채택값으로 갱신한다. 폰트·아이콘·자산의 출처와 라이선스를 보존한다.

**완료 기준:** 기준 화면의 인상을 유지한 채 공통 표현을 재사용할 수 있다. 토큰 선언만 있거나, 공통화 후 실제 화면의 비례가 달라지는 상태는 완료가 아니다.

### 5.1. CSS·Canvas 구현 원칙

스타일은 책임을 가진 기존 파일부터 정리한다. `--teal`을 한 색으로 일괄 치환하지 않고 행동·선택·자료·상태 토큰을 구분한다. 필요 없는 우선순위 경쟁이나 `!important` 덮어쓰기를 누적하지 않는다.

기존 비계층 CSS를 둔 채 새 CSS만 `@layer`에 넣으면 로딩 순서만으로 우선순위가 해결된다고 가정하지 않는다. 현행 캐스케이드에 맞게 적용하며, 계층 개편이 필요하면 영향 범위를 함께 확인한다. [W5]

`visual-theme.js`는 뷰 초기화·테마 적용 시 CSS 토큰을 읽고, 채널·분석 상태의 표시값을 해석해 화면과 PNG 생성에 전달하는 정도로 시작한다. 매 샘플마다 스타일을 다시 읽지 않는다. 저장된 정의 사본의 오래된 색과 새 테마의 우선순위를 표시 계층에서 처리한다. 단위·정밀도·원자료를 테마 객체에 복제하거나 저장 파일을 수정하지 않는다.

## 6. V3 — 준비 화면 전체 적용

**목표:** V1에서 확인한 장면을 실제 준비 안내와 연결한다.

- 검토한 카메라·조명·구도·표면을 바탕으로 준비 화면을 설계한다. 안내·단계·버튼의 위치도 장면과 함께 조정한다.
- 정확한 배선·USB·보정·수신 안내가 실제 상태를 반영하게 한다. 분위기 장면과 자세한 배선 확인의 역할을 분리할 수 있다.
- 내장 센서·BMP280·게이뤼삭의 차이를 기존 모듈에서 반영한다. 모든 센서를 같은 하드웨어 그림으로 표현하지 않는다.
- 단계 이동, 도움말, 키보드 초점, 화면 크기 변경을 확인한다. 뷰어 재생성·초기화 깜빡임·상태 손실을 막는다.
- 정적 자산과 실제 조작이 필요한 3D의 역할을 나누고 로딩·성능을 살핀다. 기존 자산만 고수해 완성도를 낮추지도, 분위기만을 위해 새 렌더링 엔진을 먼저 도입하지도 않는다.

**완료 기준:** 남색 배경을 추가한 수준이 아니라 장비 장면과 안내의 완성도가 함께 확보된다. 큰 화면과 작은 화면 모두 준비 행동을 수행할 수 있다.

**검증:** 변경한 준비 단계·단계 전환·도움말·뷰어 수명·가독성. 외형 검토를 실물 하드웨어 검증으로 보고하지 않는다.

## 7. V4 — 분석·해석·홈·저장·출력 확장

**목표:** 기준 화면에서 검증한 문법을 각 화면의 실제 작업에 맞게 적용한다.

- 분석 화면의 표·그래프·도구·탭을 필요에 따라 재배치한다. 자료의 선택/적용, 포함/제외, 추세선·연장선의 의미는 보존한다.
- 결과 해석의 글자·입력·근거 표시를 정리한다. 학습 문항과 판단의 의미를 시각 변경 때문에 바꾸지 않는다.
- 홈·저장 목록은 센서/활동 선택, 기존 실험 이어하기, 파일 접근을 제공하면서 배치와 표현을 재설계할 수 있다.
- 도움말·팝오버·모달·오류·빈 상태까지 표현을 연결한다. 보기 좋은 정상 상태만 새 테마로 남기지 않는다.
- 화면 밖에서 생성하는 분석 PNG에도 같은 글자·채널·포함/제외·추세선 규칙을 적용한다. 출력은 명료한 흰 자료 바탕으로 만들고 장식용 앱 배경은 제외한다.

**완료 기준:** 준비→측정→분석→저장의 실제 흐름에서 디자인이 일관되고, 과거 실험을 열어도 표현이 섞이지 않는다. 모든 화면을 같은 카드 격자로 만들 필요는 없다.

**검증:** 변경한 탐색과 조작, 구간 선택·적용, 제외/복원, 보기 전환, 되돌리기, 해석 보존, PNG, JSON/CSV의 내용 보존. 공통 차트 변경이 영향을 주는 경로를 함께 검사한다.

## 8. V5 — 통합 검토와 기본 적용

**적용 상태(2026-10-25):** 기본 진입 전환과 관련 검토를 완료했다. 실제 확인 범위·수치·미확인 환경은 [V5 검토 기록](review/v5/review.md)을 따른다. 아래는 단계의 작업 기준이다.

- 기준 화면과 확장 화면의 실제 캡처를 비교한다. 전체 비례·시각적 위계·장면의 품질·상태 표현이 함께 유지되는지 확인한다.
- 대비·키보드 초점·200% 글자 확대·작은 화면·모션 감소·필터 없음·폰트 로딩 실패를 확인한다. 선명한 디자인을 위해 글자를 줄이는 식의 우회를 정리한다.
- 같은 모의 자료와 같은 환경으로 값 갱신·차트·표 스크롤·뷰 전환을 비교한다. 기준 캡처만으로 성능이나 하드웨어 동작이 검증되었다고 추정하지 않는다.
- 이전 하드코딩 색·중복 선언·사용하지 않는 토큰·임시 비교 코드를 정리한다. 보존할 작은 개발 표본은 실제 부품을 사용하도록 유지한다.
- 검토를 마친 뒤 새 디자인을 기본 적용하고 문서·외부 자산 고지·시각 기준 캡처를 채택 결과에 맞춘다. 사용자용 테마 설정을 만들 필요가 없다면 개발용 전환 장치는 정리한다.

**완료 기준:** 시각 검토와 대표 기능·상태·출력 검토를 구분해 마친다. 미확인 환경은 남긴다. 모든 환경을 검증했다고 일반화하지 않는다.

**검사 전략:** AGENTS.md에 따라 변경 영향이 있는 경로부터 검사한다. 타입·의존성 변경은 타입 검사, 산출물 변경은 빌드를 포함한다. 전체 검사는 커밋 직전에만 실행하고 동일 상태에서 반복하지 않는다. 문서 개정만 한 작업을 앱 검사 완료로 보고하지 않는다.

## 10. 대표 검토 범위

모든 조합을 곱집합으로 검사하지 않는다. 공통 부품 상태는 작은 표본으로, 화면 비례와 동작은 실제 사용 경로로 확인한다.

| 경로 | 주요 확인 | 대표 화면 크기 |
|---|---|---|
| 측정 기준 | BMP280 2채널, 기록 전·기록 중·일시정지·수신 끊김 | 1366×768, 1024×768 |
| 측정 확장 | 1채널·벡터 다채널, 큰 값·음수·긴 단위·값 없음 | 1366×768, 390×844 |
| 준비 | 대표 장면, 배선/USB·내장 센서·보정, 단계 이동·뷰어 수명 | 1366×768, 768×1024 |
| 분석 | 표/그래프, 구간 선택·적용, 포함/제외·추세선·PNG | 1366×768, 1024×768 및 출력 |
| 해석·저장·오류 | 긴 한국어, 빈 상태, 저장 실패, 파일 오류 | 1366×768, 390×844 |
| 접근성·동작 | 초점·읽기 순서·200% 확대·320px 재배치·모션 감소 | 영향받은 대표 화면 |

화면 크기는 출발점이며 실제 사용 환경에 따라 조정한다. 표처럼 2차원 구조가 필요한 영역은 명시적인 내부 스크롤을 검토한다. 작은 화면의 문제를 무조건 폰트 축소로 해결하지 않는다.

## 11. 검토 자료와 결정 기록

기준 시안의 해당 화면과 실제 앱의 전체 캡처를 비교한다. 같은 자료·상태·뷰포트를 사용하되 기존 배치를 유지할 필요는 없다. 장식용 랜딩 화면만으로 새 디자인을 완료 판정하지 않는다.

‘문서 준수’, ‘토큰 구현’, ‘테스트 통과’와 ‘시각적 완성도 확인’을 구분한다. 화면이 충분히 좋아지지 않았다면 기존 치수나 배치를 지킨 사실로 완료를 대신하지 않는다.

## 14. 기본 UI 구조 전환 계획

**상태:** 1차 HTML·초기 로딩과 호출부 전환을 구현하고 관련 검증을 마쳤다. 기존 Chrome 제어 세션에서 멈췄던 5개 묶음은 독립 Chromium에서 조건 변경 없이 통과했다. 결과 해석의 높이 분배도 수정했다(§14.8). 전체 검사·커밋·배포는 하지 않았다. 2차 CSS 통합과 보관 분리를 적용·검증했다(§14.9). 3차 공통 조작·공간 배분·CSS 전달까지 적용·검증했다(§14.10). 설계 기준 커밋은 `b139daa`이며 현재 Luminous 외관과 준비 B안을 기본 구조로 정착시키는 후속 작업이다.

### 14.1. 전환 전 구조와 전환 목적

- `lab.html`은 기존 기본 CSS를 먼저 선언하고, `bootstrap.js`가 실행된 뒤 `prepareLuminousShell()`이 새 CSS를 삽입하고 조작부를 옮긴다. 초기 HTML에 기본 테마 속성도 없어 기존 버튼이 먼저 그려질 수 있다.
- `luminous.css`의 추가 CSS 요청과 글꼴 대기 뒤 Controller를 생성한다. 처음 문서를 그리는 단계와 사용할 수 있는 상태 사이를 명시적으로 구분하지 않는다. 이번 원인 분석은 코드 경로 확인이며 네트워크 지연 시간을 실측한 결과는 아니다.
- 홈·센서·활동의 배포 진입점은 같은 `lab.html`에서 생성된다. 한 템플릿을 고치되 하위 경로의 자원 주소도 함께 보존해야 한다.
- UI 검사는 현재 공통 fixture에서 같은 화면 재구성을 사용한다. 초기 화면의 중간 표시를 검증하는 계약은 아직 없다.
- A안은 별도 개발 경로에 있지만 실제 준비 View와 공통 CSS에 의존한다. 경로 분리만으로 스타일 삭제에 안전한 상태는 아니다.

목표는 첫 표시부터 현재 UI를 사용하고, 새로운 기능이 기존 역할·부품·배치 규칙을 재사용하게 하는 것이다. 기록 시작 방식, 원자료·사건·분석·파일 호환성과 Session/RunStore/Repository/Workspace의 소유권은 유지한다. 기능 추가, 시안 재선정, 프레임워크 교체, 전면 파일명 변경은 이번 범위에 포함하지 않는다.

### 14.2. 1차 — 기본 HTML와 초기 로딩

**구현 경계:** `lab.html`에 최종 구조·테마·스타일을 선언하고 `luminous-shell.js`는 제거했다. `app-shell.js`는 Controller 수명에 묶인 조작 연결만 맡는다. `startApp()`은 스타일과 서체 결정을 거친 뒤 Controller를 만들고 `ready`로 최초 경로 적용을 기다린다. 의존성 없는 bootstrap은 모듈 로딩 실패도 복구 안내로 연결한다. HTML의 정적 안내는 스크립트 자체가 실행되지 않아도 남는다. 글꼴 대기는 최대 3초 뒤 시스템 서체로 확정하며, 15초 이상 시작 대기는 새로고침 안내를 보여 주되 조작을 임의로 열지 않는다.

개발 진입점과 전체 앱 fixture도 `startApp()`을 사용한다. 컴포넌트 fixture만 명시적으로 Controller를 생략한다. 측정 개발 페이지의 옛 `theme=legacy` 분기는 이 호출부 전환에서 제거했고 기존 캡처·기준 커밋을 보관 기준으로 삼는다. 준비 A안의 별도 경로·구현·캡처는 유지했다. 아래는 1차 구현·검증의 계약이다. 이후 2차 CSS 통합은 §14.9에서 완료했다.

**고정 구조 이전:** `luminous-shell.js`가 만드는 사이드바·헤더 도구·파일 저장 메뉴·장치 설정창·측정 계기 묶음·그래프·메모 배치를 `lab.html`에 직접 둔다. 기존 조작을 복제하지 않고 최종 위치에 한 번 선언하며 ID·라벨·접근성 관계를 유지한다. 센서별 값·활동 버튼·준비 안내·저장 목록 등은 기존 View가 계속 생성한다.

**초기 자원:** HTML에 기본 테마와 새 디자인 CSS를 선언한다. 이 단계에서는 기존 CSS 뒤에 최종 디자인 CSS를 두어 현재 우선순위를 보존한다. 런타임 CSS 삽입과 고정 DOM 재배치는 제거하고 메뉴·대화상자 동작 연결만 남긴다. CSS 통합·파일명 정리는 2차로 미룬다.

**첫 표시와 실패 처리:**

| 상황 | 목표 표시·동작 |
|---|---|
| 문서 도착·초기화 대기 | 현재 디자인의 고정 틀과 짧은 준비 안내를 표시한다. 문구·경로가 아직 정해지지 않은 영역만 준비 상태로 두고, 연결되지 않은 조작은 비활성 또는 inert로 보호한다. |
| 초기 경로·문구·이벤트 연결 완료 | 해당 화면을 표시하고 안내를 해제한다. `createController()` 반환만으로 준비 완료를 판단하지 않고 최초 경로 적용·렌더 완료를 기준으로 한다. |
| JavaScript 비활성 또는 초기 모듈 로드 실패 | HTML의 안내가 남고 재시도 방법을 읽을 수 있어야 한다. `noscript`와 모듈 실행 전 실패 경로를 포함한다. |
| 필수 CSS·초기화 실패 또는 장시간 대기 | 무한 대기나 빈 화면 대신 간단한 오류·새로고침 안내를 제공한다. 초기 안내는 실패한 앱 CSS/모듈에만 의존하지 않는다. 자동 새로고침은 하지 않는다. |
| 글꼴·장식 이미지 실패 | 시스템 서체·대체 설명·예약된 이미지 영역으로 계속 진행한다. 앱 전체를 숨기거나 사용할 수 없게 만들지 않는다. |

초기화 상태는 bootstrap이 표시 수명만 관리한다. 연결·기록·저장 상태를 복제하지 않으며, 첫 렌더 완료를 알릴 통로가 필요하면 Controller의 기존 초기화 경로에서 제공한다. 문구는 공통 문구 체계를 사용하고, JavaScript 이전에도 필요한 최소 안내만 HTML에 둔다. 고정 시간 뒤 무조건 화면을 드러내는 방식은 사용하지 않는다.

글꼴 준비는 화면 틀 표시와 Canvas 생성을 분리한다. 관련 글꼴의 로드 또는 대체 서체 결정을 한 번 확정하고 화면 그래프·PNG·인쇄가 같은 결정을 사용한다. 글꼴 대기에 상한을 두고 실패 시 대체 서체로 진행하며, 매 수신마다 스타일을 조회하거나 뒤늦은 로드 때문에 전체 그래프를 반복 생성하지 않는다. 이 정책으로 [디자인 문법의 출력 일치 계약](visual-language.md#6-dom과-canvas의-연결)을 유지한다.

**함께 갱신할 호출부:** 실제 bootstrap, `dev/design/load-lab.js`와 측정·준비 검토 진입점, `tests/browser/lab-fixture.js`, `scripts/entry-pages.mjs` 및 배포 생성 경로. fixture는 바뀐 실제 템플릿·스타일·공통 초기화를 사용하며 옛 DOM 조립기를 남겨 테스트만 통과시키지 않는다. 문서 전체 부팅과 UI 컴포넌트 검사의 범위를 구분한다.

**완료 기준:** 홈과 센서·활동 직접 진입에서 기존 버튼·도구 배치가 중간에 노출되지 않는다. 캐시 없는 접속과 자원 지연·실패에도 안내가 남는다. 기본 화면과 출력의 표현을 유지하고, 설정창 이동·닫기·초점 복귀·파일 메뉴 동작과 자원 하위 경로가 정상이다. 초기화 전 조작이 기록·DB 생성을 시작하지 않는다.

### 14.3. 2차 — CSS 소유권 통합과 보관 분리

**적용 완료:** 2026-10-25, 아래 기준으로 통합했다. 구현·검증 범위는 [§14.9](#149-2차-css-소유권-통합-적용)를 따른다.

통합 책임은 [디자인 문법 §8](visual-language.md#8-기본-ui의-목표-구조)을 따른다. 공통 조작 → 준비 → 측정 → 분석·해석 → 홈·보관 순으로, 한 범위의 기존 선언과 덮어쓰기에서 최종 동작을 확인하고 담당 파일로 합친다. 동적 대화상자와 PNG·인쇄도 사용처에 포함한다. 정상 상태만 보고 오류·비활성·초점·확대·인쇄 규칙을 지우지 않는다.

원칙은 같은 역할·상태를 한곳에서 정의하는 것이다. 밝고 어두운 표면의 값 변경과 화면별 크기 차이는 필요한 차이로 유지한다. `--ink` 등 이전 별칭과 테마 분기는 소비 경로를 옮긴 뒤 정리한다. 초기 단계의 기본 테마 속성과 `readVisualTheme()` 계약은 일괄 제거하지 않는다.

**A안 보관:** 사용자 시안, 최초 A/B 캡처, `dev/design/archive/preparation-a.html`과 실행 가능한 A안 표현을 유지한다. 삭제 예정인 CSS에 의존하는 A안의 표현은 삭제 전에 archive 전용 스타일로 옮긴다. 공통 준비 기능·모의 장치는 재사용하고 앱 전체나 데이터 엔진을 복제하지 않는다. 기본 진입점은 A안 자원을 요청하지 않으며 개발 코드는 기존처럼 배포 대상에서 제외한다. 문서·캡처의 배포 여부와 개발 코드 제외는 구분한다.

기존 측정 `theme=legacy` 비교는 기본 개발·검사 경로에서 분리한다. 원본 표현은 기준 커밋과 캡처로 보관하고, 실행 비교를 유지할 때만 archive 전용 진입점에서 제공한다. 이를 위해 운영 CSS에 옛 표현 분기를 남기지 않는다. A안의 실행 보존과 옛 측정 UI 비교는 별개의 요구다.

**완료 기준:** 해당 부품의 모양을 수정할 담당 규칙이 명확하고, 이전 선언을 덮기 위한 불필요한 재정의가 제거된다. 같은 자료·상태·화면 크기에서 채택한 외관이 유지되고 A안도 별도 경로에서 열린다. 사용자 경로에 A안 선택이나 legacy 분기가 다시 생기지 않는다.

### 14.4. 3차 — 공통 부품·반응형 확장과 로딩 비용 정리

**적용 완료:** 아래 기준의 결과와 확인 범위는 [§14.10](#1410-3차-재사용공간-배분스타일-전달-적용)을 따른다.

- 버튼·탭·메모·입력·메뉴·대화상자는 기존 역할과 상태 처리를 재사용한다. 실제 여러 곳에 쓰이는 부품부터 통합하며 임의의 새 범용 컴포넌트 계층은 만들지 않는다.
- 최대 폭과 상하단 조작의 필요 높이를 확보하고 그래프·표에 남는 공간을 배분한다. 최소 읽기 크기, 상세 내용, 작은 화면·200% 글자의 스크롤은 보장한다. 화면마다 별도의 고정 높이 보정을 계속 추가하지 않는다.
- DOM·범례·Canvas·PNG·인쇄의 역할 토큰 전달을 유지한다. 동일 물리량·단위의 방향 성분과 크기는 같은 축·스케일을 사용하고, 표시 항목 변경으로 자료색이 재배정되지 않게 한다.
- 초기 자원 요청과 화면 안정화 비용을 측정한 뒤 CSS `@import` 경로의 통합·배포 묶음을 판단한다. 소스는 책임별로 유지하고, 배포 CSS를 묶으면 개발과 배포의 순서·상대 자원 주소가 같아야 한다. 단순히 파일 수를 줄이기 위한 빌드 도구 도입은 하지 않는다.
- 3D 등 무거운 자원은 필요한 화면에서 로드한다. 초기 틀을 위해 분석·출력·장식 자원을 모두 선로딩하지 않는다. 라이선스와 출처를 보존한다.

**완료 기준:** 새 화면 조작을 기존 역할 조합으로 추가할 수 있고, 밝은 자료 화면과 준비 B에서 같은 조작 의미를 유지한다. 넓은 화면의 불필요한 스크롤을 줄이면서 작은 화면의 내용 접근성을 보존한다. 성능 개선은 같은 조건의 전후 관찰로 보고하고 수치 목표나 개선율을 미리 단정하지 않는다.

### 14.5. 검증과 단계 종료

| 영향 | 확인할 동작과 기존 검사 재사용 |
|---|---|
| 최초 문서 표시 | 실제 문서 탐색의 초기 프레임·자원 지연·실패를 확인한다. 기존 iframe 검사의 준비 완료 후 확인만으로 대체하지 않는다. 반복 가능한 초기 표시 회귀 사례를 기존 브라우저 검사에 보완한다. |
| 고정 조작부·초기화 | `app`, `navigation`, `records`를 중심으로 실제 조작·저장 실패·이탈 취소·설정창 해제·첫 경로를 확인한다. 바뀐 템플릿/fixture가 쓰이는 준비·측정·분석 검사는 해당 영향에 맞춰 선택한다. |
| 표현과 크기 | 기존 `preparation`, `luminous`, `workspace`, `accessibility` 중 변경 화면을 선택한다. 1366×768 기준 화면과 좁고 낮은 화면·글자 확대를 비교한다. |
| Canvas·출력 | `measurement`, `ui`의 자료·축·색·서체·근거 보존과 출력 일치를 재사용한다. |
| 성능·빌드 | 비용 변화가 있는 단계에서만 기존 `performance`를 사용한다. HTML 진입점이나 CSS 배포 방식 변경 시 빌드·프로젝트 하위 경로를 확인한다. |

첫 화면 회귀는 표시와 조작 가능 상태를 검사한다. CSS 소스 문자열, 파일명, 임시 DOM 위치만 고정하는 테스트는 추가하지 않는다. 자원 지연·실패 주입은 개발·검사 경계에만 두고 사용자용 테마나 쿼리 옵션으로 확장하지 않는다.

작업 중에는 영향 있는 검사만 수행하고, 전체 검사는 커밋 직전에만 실행한다. 사용자가 검사 생략을 명시하면 해당 지시를 따른다. 이전 검사 통과를 이번 변경의 결과로 보고하지 않는다. 실물 USB/BLE·실제 프린터 검증은 모의 브라우저 검사와 구분한다.

각 차수는 독립적으로 검토할 수 있는 범위에서 마무리한다. 기존 캡처와 현재 구현의 차이를 확인하고, 단기 스크립트·검토 DB를 정리한다. **현재 구현 범위는 1차 HTML·초기 로딩, 호출부 갱신, 독립 브라우저 검사와 결과 해석 높이 분배, 2차 CSS 소유권 통합·A안 스타일 분리, 3차 공통 조작·공간 배분·CSS 전달까지**다. 초기 시작 검사, 직접 진입, 준비 B와 보관 A의 시각 확인은 아래 기록을 따른다. §14.8에서 남아 있던 5개 묶음을 확인했으며 저장소 전체 검사와 구분한다. 2차 검증은 §14.9, 3차 검증은 §14.10을 따른다.


### 14.6. 로컬 서버 재시작 후 브라우저 검증

- `startup` 5개: 준비 전 조작 잠금·최초 경로 완료 후 공개, CSS/시작 모듈 실패 안내, 글꼴 실패 대체, 스크립트 미실행 안내 통과.
- `ui` 8개, `app` 9개, `navigation` 4개, `records` 5개와 `guide` 앞 3개 항목 통과. 첫 실행에서 총 34개 항목을 확인했다. PNG/인쇄는 실제 Canvas 표현 일치 검사이며 실물 인쇄 결과가 아니다.
- `guide`, `luminous`, `preparation`, `workspace`, `accessibility`는 iframe 하위 문서 로딩 실패로 미통과. 당시 하위 문서는 `about:blank`에 머물렀다. 실패 묶음을 새 문서에서 독립 실행해도 재현되었으며, 준비 B의 BMP280 1366/390px 단계·도움말·모의 수신·상태/초점 유지 항목은 이 재실행에서 추가 통과했다. 조건을 완화하거나 검사를 제거하지 않았다. 앱 또는 검사 실행 환경 중 어느 쪽 원인인지는 확정하지 않았다.
- 일반 탭 직접 확인: 원본과 `dist/`의 홈·내장 온도 센서·게이뤼삭 활동 총 6개 경로가 오류 없이 준비 완료에 도달했다. 빌드 활동 경로 새로고침도 확인했다. 측정 장치 이미지, 설정창 열기·닫기·초점 복귀, 분석/원자료 전환, 준비 B의 3D 배선 적용과 접지 단계 이동, 보관 A의 프로그램 화면이 정상 표시됐다.
- 화면 크기 직접 확인: 1366×768에서 관계 그래프·원자료 화면은 페이지 높이 768px였다. 결과 해석은 1023px로 세로 스크롤이 남았다. 이 표현 문제는 수정하지 않았으며 후속 배치 검토 항목으로 남긴다. 390px의 측정·해석과 200% 글자/글꼴 실패/동작 줄이기 검토 화면은 가로 넘침이 없었다. 대체 서체로 준비 완료에 도달했다. 이는 전체 `accessibility` 묶음 통과를 대신하지 않는다.
- 검토용 자료는 각 페이지의 정리 동작으로 제거하고 임시 화면 크기를 복원했다. 이 차수에서는 앱 코드·검사 조건 변경이나 커밋·배포를 하지 않았다. 실물 USB/BLE와 실제 프린터는 확인하지 않았다.

### 14.7. 근본 개선안 — 실제 페이지 검사와 공간을 소유하는 화면 구조

**상태: 최초 조사·제안 기록.** 2026-10-25에 현재 코드와 아래 공식 문서를 대조했다. 당시 `about:blank`의 원인은 미확정이었다. 아래 제안 중 실제로 적용하고 확인한 범위는 §14.8에서 구분한다. 최상위 페이지로 기존 검사를 모두 이관하거나 전체 CSS 공간 구조를 전환한 상태는 아니다.

#### 확인한 약점과 유지할 기반

- 전체 앱 크기 검사가 앱을 검사 페이지 안의 iframe에 넣어 실행한다. 실제 사용자 진입과 달리 부모 문서·하위 문서의 두 수명을 관리하며, 여러 묶음은 준비 표시만 반복 확인해 문서 탐색 실패와 앱 초기화 실패를 구별하지 못한다. 컴포넌트 fixture는 실제 HTML을 재사용하지만 같은 문서의 스타일·서체 상태 복원을 직접 관리한다.
- 배포 workflow는 현재 타입·단위 검사·빌드를 실행하며 브라우저 검사는 자동 배포 조건에 포함하지 않는다. 수동 브라우저 검사와 배포의 품질 확인 경로가 분리되어 있다.
- iframe의 `load`는 내용 로드 실패에도 발생할 수 있고 `error`는 신뢰할 수 있는 네트워크 실패 신호가 아니다. 이 둘만으로 성공·실패를 판정하는 설계를 확장하지 않는다. 현재 3D 어댑터는 이미 출처·발신 창·버전·요청 ID와 `ready`/`applied` 응답을 검사하므로 그 계약을 재사용한다. 합성 `error` 이벤트를 보내는 검사는 분기 검증이며 실제 네트워크 실패 검증으로 간주하지 않는다. [MDN iframe 이벤트](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe#error_and_load_event_behavior)
- 높이 계산은 관계 그래프의 `createAnalysisLayout()`에 집중되어 있다. 원자료에는 `100dvh - 530px` 같은 별도 보정이 있고, 결과 해석에는 고정 그래프 높이·질문 여백·입력란 최소 높이가 쌓인다. 재사용할 공간 계약이 화면마다 다르다.
- 정적 HTML·공통 시작 경로·기존 ESM 모듈·토큰·공통 메뉴·장치 어댑터는 유지한다. 새 프레임워크나 앱 상태 저장소로 옮길 근거는 현재 문제에서 확인되지 않았다.

#### 검사 책임 재배치

| 범위 | 제안한 실행 방식 | 보존할 계약 |
|---|---|---|
| 계산·원자료·저장·파일 계약 | 기존 Node 단위 검사와 필요한 브라우저 저장 검사 | 현재 회귀 사례와 오류 복구, 수치·파일 호환성 |
| 개별 View 조작 | 기존 실제 HTML fixture를 필요한 범위에서 유지 | 모의 입력·원자료 보존·Canvas/출력 일치 |
| 초기 접속·화면 이동·반응형·확대 | Playwright Test의 독립 BrowserContext에서 실제 앱을 최상위 페이지로 열기 | 실제 입력·초점·화면 크기 변경·직접 진입·재진입 |
| 제품 안의 3D iframe | 실제 앱에서 배선 화면을 열고 자식 문서와 응답 확인 | 3D 지연 로드, 출처 검증, 단계 적용, 실패 후 배선표·재시도 |

Playwright Test는 개발 의존성으로 제안한다. 앱 배포 자원에는 넣지 않는다. 기존 모의 장치·자료 생성·의미 있는 검증은 재사용하고, 먼저 실패한 경로만 옮긴다. 이전 검사를 삭제하기 전에 원래 보호하던 동작이 새 실행 경로에서도 검사되는지 대응표로 확인한다. 단위 검사 전체나 개발 A/B 검토 페이지를 다시 만들지 않는다. [격리된 브라우저 환경](https://playwright.dev/docs/browser-contexts), [사용자 동작·자동 대기 기반 검증](https://playwright.dev/docs/best-practices)

고정 지연 후 성공을 가정하지 않고 앱 준비 상태와 실제 조작 가능 상태를 기다린다. 전체 앱 준비와 3D 준비, 장치 수신 준비는 별개다. 기록이 지속되는 앱에 네트워크가 한동안 조용하다는 조건을 공통 준비 기준으로 쓰지 않는다. 실패 시 요청 URL·응답 상태·요청 실패·최종 프레임 URL·콘솔 오류·화면 상태를 추적으로 남긴다. HTTP 오류 응답과 요청 자체의 실패를 구별하고, 재시도로 통과한 불안정 사례도 남긴다. [네트워크 관찰](https://playwright.dev/docs/network), [Trace Viewer](https://playwright.dev/docs/trace-viewer)

**진단을 먼저 하는 최소 비교:** 같은 로컬 서버와 동일한 배선/검토 URL을 대상으로 현재 실행 환경과 새 독립 브라우저 환경을 비교한다. 기존 iframe 실패도 추적을 남긴 뒤 다음 기준으로 수정 대상을 결정한다.

| 관찰 결과 | 다음 확인·수정 대상 |
|---|---|
| 하위 문서 요청이 시작되지 않거나 탐색이 취소됨 | frame 삽입·제거·재사용 순서, 상위 문서 이탈, 브라우저 제어 환경 |
| 요청 실패 또는 HTTP 오류 | 자원 경로·서버 응답·실제 콘솔의 차단 원인 |
| 정상 문서 응답 후 앱 준비 실패 | 모듈 예외·스타일·초기 경로와 시작 수명 |
| 앱은 준비됐지만 3D 응답 실패 | 뷰어 문서·WebGL·준비/적용 응답과 요청 수명 |
| 독립 실행은 성공하고 특정 제어 환경에서만 실패 | 실행 환경의 재현 사례로 분리. 앱 보안 정책이나 준비 판정을 완화하지 않음 |

정식 실행이 안정화되면 배포 전 브라우저 검사도 같은 명령으로 연결한다. 현재 구조 전환 작업 중에는 영향 있는 묶음만 실행하고, 전체 검사는 기존 커밋 전 규칙을 따른다. 브라우저 버전과 의존성은 실행마다 달라지지 않게 고정한다. Chromium을 장치 연결 경로의 우선 대상으로 삼되 UI·파일 분석은 Firefox/WebKit에서도 별도 확인하는 것을 제안한다. WebUSB/Bluetooth는 모든 주요 브라우저에서 같은 지원을 보장하지 않으므로 기능 감지와 실물 검증을 UI 검사와 구분한다. [Playwright CI](https://playwright.dev/docs/ci-intro), [Web Bluetooth](https://developer.mozilla.org/en-US/docs/Web/API/Web_Bluetooth_API), [WebUSB](https://developer.mozilla.org/en-US/docs/Web/API/WebUSB_API)

#### 화면 공간의 소유권

| 소유자 | 책임 |
|---|---|
| 앱 틀 | 문서 최대 폭, 내비게이션·헤더, 뷰포트와 본문의 공간 관계 |
| 분석 작업 영역 | 상단 조작·내용·하단 행동의 행 배치, 그래프·표·해석에 배정할 공간 |
| 개별 부품 | 자기 컨테이너 폭에 따른 줄바꿈·가로/세로 배치, 읽기·입력 최소 크기 |
| 차트 어댑터 | 배정된 영역에 Canvas를 맞춤. 페이지 전체 여백을 다시 결정하지 않음 |

CSS Grid/Flex와 동적 뷰포트 단위를 먼저 활용한다. 데스크톱에서 상단·하단 행은 내용 크기를 확보하고, 남는 공간은 그래프·표가 사용한다. 자료 영역의 `minmax(0, 1fr)`·`min-inline-size:0`·`min-block-size:0`는 내부 콘텐츠가 배치를 밀어내지 않도록 필요한 범위에 적용하되 입력란·제목까지 무조건 줄이지 않는다. 내용이 최소 읽기 크기를 넘는 경우 페이지가 자연스럽게 늘어나도록 한다. 기존 화면별 고정 뺄셈과 JS 높이 계산은 동작이 이관된 범위부터 정리한다. Canvas/가상 표의 실제 크기 반영에는 기존 ResizeObserver를 재사용하고 측정·쓰기의 순환 갱신을 피한다. [뷰포트 단위](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/length), [ResizeObserver](https://developer.mozilla.org/en-US/docs/Web/API/ResizeObserver)

부품의 가로 배치 여부는 창 전체 폭보다 배정된 컨테이너 폭으로 판단한다. 현재 이미 사용하는 `container-type:inline-size`와 크기 쿼리를 공통 조작에 확장한다. 페이지의 큰 열 구성은 미디어 쿼리/Grid가, 축 조작·통계·버튼 묶음의 배치는 컨테이너 쿼리가 맡는다. 내용으로 높이가 정해지는 카드에 무분별하게 `container-type:size`를 적용하지 않는다. [MDN 컨테이너 쿼리](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Containment/Container_queries)

결과 해석은 근거/저장·인쇄 영역과 글쓰기 영역의 실제 최소 높이를 각각 확인한다. 지금 255px 넘친다는 관찰만으로 그래프 높이를 그만큼 줄이거나 글자를 축소하지 않는다. 기본 상태의 질문 카드 여백·입력란 시작 크기를 조정하고, 긴 답변·긴 활동 안내·확대 상태에는 페이지 세로 스크롤을 허용한다. 기본값을 화면에 맞추더라도 작성된 글을 자르거나 세 질문 각각에 강제 스크롤을 만들지 않는다. 초기 상태를 맞추기 위한 질문 접기·단계 전환은 사용자 경험 변경이므로 별도 합의 없이 도입하지 않는다. 320px 폭에서의 재배치와 200% 글자, 실제 브라우저 확대도 구분해 확인한다. [W3C Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

#### 적용 순서와 종료 조건

1. 실패 경로 한 개에서 원래 iframe과 실제 페이지의 추적을 확보하고 원인을 분류한다. 이 단계에서 앱의 iframe을 삭제하거나 모든 검사를 옮기지 않는다.
2. 초기 진입·준비·측정·분석의 핵심 흐름을 독립된 실제 페이지 검사로 이관한다. 보존된 A안과 실제 3D iframe은 별도 필요한 사례로 유지한다.
3. 공통 작업 영역의 공간 계약을 정리하고 결과 해석에 먼저 적용한다. 정상 상태·긴 내용·작은 화면·확대 상태를 확인한 뒤 원자료·관계 그래프의 중복 높이 보정까지 통합한다.
4. 실패한 5개 묶음의 보호 범위를 빠짐없이 확인하고, 실행 환경 문제는 재현 근거와 함께 별도 기록한다. 그 뒤 2차 CSS 소유권 통합을 이어간다. 검사 기반 개선과 화면 구조 수정을 한 번에 전면 교체하지 않는다.

이 최초 조사에서는 런타임·테스트 코드·의존성·배포 설정을 변경하지 않았다. 이후 원인 추적과 적용 결과는 다음 절을 따른다.

### 14.8. 탐색 실패 분리와 결과 해석 수정

2026-10-25, 사용자의 원인 추적·해결 요청에 따라 진행했다.

- **원인 범위:** 앱 코드·스타일이 전혀 없는 단순 HTML iframe도 기존 Chrome 제어 세션에서는 첫 탐색 후 연속 탐색 3건이 `about:blank`에 남았다. 서버는 모두 HTTP 200을 반환했다. 삽입 전/후 `src` 지정 순서를 바꿔도 재현됐고, 실제 버튼 클릭마다 단일 탐색하면 성공했다. 같은 8080 서버·같은 문서·같은 연속 탐색을 독립 Chromium에서 실행하면 4건 모두 완료됐다. 앱 초기화 이전의 실행 환경 문제로 분리했으며, 특정 확장 기능이나 브라우저 내부 원인까지 확정한 것은 아니다.
- **검사 실행:** 개발 의존성 `@playwright/test` 1.64.1과 해당 Chromium 빌드를 고정했다. `playwright.config.mjs`는 8081의 별도 서버, 검사별 BrowserContext, 재시도 0회, 실패 trace·화면을 사용한다. 기존 `startup`, `guide`, `preparation`, `luminous`, `workspace`, `accessibility`의 검증 조건을 그대로 실행하며 앱의 준비 판정이나 3D 출처 검사를 완화하지 않았다. 기존 iframe 검사를 전면 삭제·이관하지 않았다.
- **실제 페이지 회귀:** 해석 화면의 1366px 높이 맞춤·320px 재배치·200% 글자 확대와 작성 내용 보존, 실제 3D 네트워크 요청 중단에 따른 배선표 복구·재시도에 집중한다. 다른 화면 크기·원자료 보존·분석 왕복은 기존 `workspace`, 3D 지연 로드·네 배선 단계·크기 변경 중 유지는 기존 `guide`/`preparation`에서 보호한다. 합성 `error` 이벤트만으로 로딩 실패를 대체하지 않는다.
- **높이 수정:** `createAnalysisLayout()`이 결과 해석에도 남은 작업 높이를 전달한다. CSS Grid/Flex가 근거 그래프·글쓰기 영역을 나누고, 질문 여백과 입력란 시작 높이를 조정한다. 글자 크기·질문·저장 위치는 유지하며 그래프는 최소 200px, 답변 입력은 최소 두 줄을 보장한다. 긴 내용·펼친 안내·확대 화면은 자연스럽게 세로로 늘어날 수 있다.
- **검증 결과:** 타입 검사·빌드 통과. `npm run test:e2e` 8개 통과(기존 6개 묶음 + 실제 페이지 2개). 기존 5개 실패 묶음 모두 독립 실행에서 통과했다. 1366×768 해석 화면은 수정 전 1023px에서 수정 후 768px로 맞았고, 최종 캡처의 그래프 높이는 216px·답변 입력란은 각 66px였다. 390px 직접 확인에서도 가로 넘침 없이 작성한 520자가 보존됐다. 전체 단위·전체 브라우저 검사와 실물 USB/BLE·프린터 검사는 실행하지 않았다.
- 임시 진단 HTML 2개를 삭제하고 요청 추적 서버를 일반 개발 서버로 되돌렸다. 제어 브라우저의 임시 크기와 검토 DB를 정리했다. 커밋·배포는 하지 않았다.
- **검사 정리:** 원인 확인 후 실제 페이지 검사의 중복 순회를 위 책임 구분에 맞춰 줄였다. 통과 결과의 반복 첨부와 trace에 이미 포함되는 별도 네트워크·콘솔 로그 수집을 제거하고 실패 때만 결과를 첨부한다. 이전 실행 산출물은 정리하며 독립 실행 기반과 유효한 회귀 검사는 유지한다.
- 정리 중 모바일에서 넓은 화면으로 돌아올 때 Canvas의 이전 높이가 Grid/Flex 최소 높이를 밀어 올리는 22px 넘침을 추가 확인했다. Canvas를 크기 계산 흐름에서 분리하고 기존 stage가 크기를 맡도록 수정했다. 이 왕복 검사는 유지하며 정리한 해석·실제 3D 실패 복구 검사 2개가 통과했다.

### 14.9. 2차 CSS 소유권 통합 적용

2026-10-25, 기본 UI의 스타일 소유권을 통합했다. 1차의 고정 DOM·시작 수명·표시 어댑터 계약은 유지한다.

- **담당 파일:** `base.css`는 문서 기본값, `controls.css`는 공통 조작 상태와 대화상자 표면, `lab.css`는 앱 틀을 맡는다. 준비·측정·분석·해석·홈/보관·편집 내용은 각각 `guide.css`·`measurement.css`·`analysis.css`·`reflection.css`·`library.css`·`dialogs.css`에 모았다. 활동 안내·메뉴·도움말은 기존 담당 파일을 유지한다.
- **정리 범위:** 별도 `luminous-controls/preparation/analysis/library.css` 4개를 제거했다. `luminous.css`는 정적 import 목록만 소유하며 실제 앱·검토·브라우저 fixture는 같은 진입을 사용한다. 사용하지 않는 이전 화면 선택자와 확실히 가려지는 선언을 제거하고 `--ink`, `--muted`, `--teal` 등 이전 별칭을 소비 경로까지 이행했다. 자기장 보정의 지역 색상도 준비 역할을 읽는다.
- **보관 경계:** A안의 밝은 준비 배치는 `dev/design/archive/preparation-base.css`로 옮겼다. 검토 로더가 준비 CSS만 교체하고 기존 A안 보정을 더한다. 공통 준비 동작·모의 장치·저장 엔진은 복제하지 않으며 사용자 시안·최초 비교 캡처를 유지한다. 기본 B안의 자기장 보정 진입에서도 archive 요청이 없음을 확인했다.
- **표현 확인:** 홈·소개·준비 A/B 각 세 단계·측정·설정·분석 세 화면·저장 목록을 1366px/390px에서 비교했다(28조합). 화면 배치·크기·가시적인 표현을 유지했다. 선 두께가 0인 일부 분석 버튼의 계산된 선 색은 달라지지만 화면에 그려지는 선은 없다. 자기장 보정 A/B의 색과 간격도 별도로 확인했다.
- **회귀 확인:** 독립 Chromium의 기존 11개 묶음(`startup`, `guide`, `preparation`, `luminous`, `workspace`, `accessibility`, `ui`, `app`, `records`, `measurement`, `navigation`)과 실제 페이지 2개가 모두 통과했다. 자기장 스타일 이행 후 준비 묶음을 재확인했다. PNG/인쇄 Canvas의 자료·표현, 저장 편집, 비활성·초점·확대·작은 화면, 실제 3D 실패 후 복구를 포함한다. 빌드와 변경 공백 검사도 통과했다. 데이터·계산 코드를 바꾸지 않아 전체 단위·타입 검사는 반복하지 않았다. 실물 장치·프린터와 다른 브라우저는 확인하지 않았다.
- **비용과 남은 단계:** 준비를 포함한 공통 UI CSS 원문은 약 170.5KB에서 146.6KB로 줄었다(약 14%, 압축 전·센서별 CSS 제외). 전송 시간 개선을 측정한 수치는 아니다. 2차 종료 당시 남아 있던 부품 재사용·작업 영역 높이·CSS 전달 정리는 이후 §14.10에서 적용했다.
- 비교·이행용 임시 스크립트와 캡처·중간 데이터는 정리한다. 유효한 기존 회귀 검사는 유지하고 내용이 같은 테스트를 새로 복제하지 않는다. 커밋·배포는 하지 않았다.

### 14.10. 3차 재사용·공간 배분·스타일 전달 적용

2026-10-25, 1–3차 구조 전환의 구현 범위를 마무리했다. 기록 시작·자료 소유권·저장 형식·센서 축 계약은 변경하지 않았다.

- **재사용:** 공통 버튼 역할을 `data-ui-action`으로 지정할 수 있게 하고, 준비·분석 탭은 `.ui-tab`의 공통 선택·호버·직각 표현을 사용한다. 준비 B의 주요 행동은 지역 팔레트에서 강조색으로 연결하고 A안의 밝은 표현을 유지한다. 사건·메모도 공통 버튼 상태에 역할 값만 연결한다. 기존 메뉴 이벤트·대화상자 편집 수명을 재사용하며 새 범용 UI 엔진이나 의존성을 추가하지 않았다.
- **공간:** `createViewportLayout()`이 측정·원자료·관계·해석의 남은 높이를 전달한다. 관계 그래프/표의 개별 높이 차감과 원자료·측정의 고정 페이지 여백 차감을 제거했다. CSS가 조작부의 자연 높이를 확보하고 그래프·가상 표에 남은 높이를 나눈다. 차트 인스턴스·원자료는 유지한다. 분석 그래프 최소 240px, 측정 256px, 해석 200px를 보존하며 긴 메모·펼친 안내·확대·작은 화면은 필요한 세로 스크롤을 허용한다. 가령 1366×768의 메모가 있는 측정 검토 화면은 최소 크기 때문에 26px의 세로 여유가 더 필요했다.
- **전달:** `scripts/styles.mjs`를 개발 서버와 정적 빌드가 함께 사용한다. 담당 CSS 파일은 유지하고 로컬 import 순서대로 결합하며 이미지·글꼴 URL을 결과 위치에 맞춘다. 준비 CSS는 별도로 두어 A안 대체 경계를 보존한다. 지원하지 않는 import·순환 참조는 실패 처리하고 조용히 순서를 바꾸지 않는다. 시작 안내·실패 경로와 3D 지연 로드도 유지한다.
- **로딩 관찰:** 동일한 독립 Chromium, 매번 새 Context, 홈/내장 온도/게이뤼삭 각 3회, 각 CSS 요청에 100ms 지연을 추가한 조건에서 최초 CSS 요청은 14개→2개였다. 9회 전체 중앙값은 첫 내용 표시 308→188ms, 앱 준비 421→322ms였다. 실제 인터넷·기기 전체의 보장값이 아니며 import 요청의 추가 대기 단계를 제거한 효과를 관찰한 것이다. 세 진입 모두 최초 화면에서 3D 자원을 요청하지 않았다.
- **검증:** 타입 검사·빌드, 스타일 결합/하위 경로 단위 검사 3개 통과. 관련 기존 브라우저 묶음 7개(startup/preparation/luminous/workspace/accessibility/ui/measurement)와 실제 페이지의 해석 재배치·3D 실패 복구 2개가 통과했다. 작업 영역 검사는 창 높이가 늘 때 그래프도 커지는 조건을 보완했다. 1366/1920/2560의 관계·원자료, 1024/390/320 재배치·200% 글자, 원자료·해석 보존, PNG/인쇄 Canvas, 같은 물리량의 채널 표시를 기존 검사로 확인했다. 개발과 `dist/` 하위 경로의 홈·센서·활동 총 6개 진입도 자원 실패 없이 준비됐고 주요 표시값이 일치했다.
