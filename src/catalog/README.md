# 센서·활동 모듈 등록

`modules.js`가 앱의 등록 지점이다. 각 센서의 `index.js`는 `definition`, `decode`,
`mockLine`, `guide`를 묶고, 활동의 `index.js`는 `definition`, `guide`, `policy`를 묶는다.
홈 목록, 일반 진입 주소, 통신 decoder, 준비 안내, 활동 policy가 이 등록을 함께 사용한다.
등록 시 중복 ID/버전, 실행 코드 누락, 활동의 필수 채널, 준비 단계 ID 충돌을 검사한다.

## 내장 센서를 추가할 때

1. `sensors/<id>/`에 측정 채널·단위·표시·연결 정책을 담은 `definition.js`, 원문을
   해석하는 `codec.js`, 준비물과 안내를 담은 `guide.js`를 만든다. 긴 문구는 `content.js`에 둔다.
2. `index.js`에서 위 파일들을 묶고 `modules.js`의 센서 목록에 한 번 등록한다.
   `/sensors/<id>/` 주소와 홈 카드는 자동으로 생긴다. build와 개발 서버도 같은 주소 목록을 쓴다.
3. 실제 프로그램 소스·검증된 HEX·해시를 준비하고 `src/device/firmware.js`의 허용 목록에
   등록한다. 이것은 장치 설치의 별도 검증 경계다. 내장 센서는
   `dev/firmware/targets.json`에 소스·규약을 추가하고 공통 빌드로 검토용 HEX를 생성한다.
   [펌웨어 빌드 절차](../../dev/firmware/README.md)에 따라 검증한 뒤 앱에 등록한다.
4. 정상·잘못된 UART 입력, 단위·범위, 모의 수신, 준비 완료 근거를 검사하고 실물에서
   설치·연속 수신을 확인한다. mock 성공을 하드웨어 검증으로 표시하지 않는다.

`definition`과 실험 context는 JSON으로 저장할 수 있는 데이터다. 함수와 뷰어 URL은
실행 모듈에만 둔다. 일반 진입에는 센서·활동의 최신 등록 버전을 사용하고, 저장된
실험의 실행 코드·안내는 ID와 버전을 정확히 찾아 사용한다. 없는 버전을 최신으로
대체하지 않는다. 기존 자료의 분석·내보내기는 저장된 정의 사본으로 계속 가능하다.

`connectionPolicy.requiredChannelIds`가 있으면 그 채널이 모두 유효해야 새 수신으로 인정한다.
빈 목록이면 하나 이상의 유효 채널을 요구한다. DS18B20의 선택적 두 번째 프로브는 이 정책을
사용하며, 연결 확인과 한 점 캡처가 같은 수신 판정을 재사용한다. 모두 결측인 행은 통과하지 않는다.

## 공통 화면과 문구

공통 요소를 만들거나 수정할 때는 [책임 분리 원칙](../../docs/unified-sensor-lab-architecture.md#공통화와-개별-기능의-책임)을 먼저 따른다.
센서·활동의 선택적 `definition.readout`은 `primaryChannelId`와 `componentChannelIds`로
현재값의 대표 항목과 방향별 성분을 선언한다. 활동 정의가 우선하며, 성분은 같은 물리량·단위의
등록 채널이어야 한다. 공통 화면은 명시된 성분에만 대표값의 대칭 눈금을 적용한다.
기본 그래프 축은 이 관계를 바꾸지 않는다. 정확히 일치하는 등록 정의가 없는 과거 자료는
첫 채널을 대표값으로 표시하고 성분을 추측하지 않으며, 저장된 채널·수치·단위는 보존한다.

준비 단계의 그림은 해당 `GuideStep.image`에 `{src, alt, caption}`으로 지정한다.
공통 화면은 단계 ID와 관계없이 그림을 표시하며 그림이 없는 단계에서는 숨긴다.
재연결의 `reconnecting`은 호출자가 명시하는 사용자 흐름의 목적이다. 이전 장치 사용,
새 장치 선택, 설치 직후 연결 인계와 독립적이며 센서 준비 모듈에 전달한다.

측정 화면 안내는 센서·활동의 `guide.experimentGuide`에 선언한다. 활동 안내가 있으면 우선하며,
공통 `ui/experiment-guide.js`가 최초 자동 표시·다시 보기·초점 복귀를 맡는다. 내장 센서 위치 안내는
각 센서의 `content.js`와 `shared/location-guide.js`를 사용한다. 한 장짜리 안내는 단계 탐색을 생략한다.

### 시간 그래프의 공통 축

채널의 `quantity`와 `unit`이 모두 명시되고 각각 일치하면 하나의 세로축과 스케일을 사용한다.
X/Y/Z 성분과 크기는 동일한 물리량 ID·저장 단위를 지정한다. 새 센서도 이 규칙을 자동 적용하며
공통 차트에 센서 ID 분기를 추가하지 않는다. `quantityLabel`에는 공통 축에 보일 한국어 물리량 이름
(예: `가속도`, `자기장`)을 선택적으로 지정한다. 묶인 채널은 같은 이름을 사용한다.

공통 축 범위는 표시 중인 모든 채널의 유효한 값으로 자동 결정한다. 크기가 음수가 아니라는 이유로
방향 성분의 음수를 자르거나 0을 축 최솟값으로 강제하지 않는다. 채널색·각 선의 이름은 유지하고
공통 축 제목은 중립색으로 표시한다. 다른 단위는 자동 변환하지 않고 별도 축을 사용한다.
물리량이나 단위가 없는 예전/가져온 정의는 이름으로 추측하여 묶지 않는다. `quantityLabel`만 없는
기존 정의는 공통 축에 `측정값 (단위)`를 표시한다. 저장된 정의·원자료는 다시 쓰지 않는다.

이 규칙은 측정과 분석의 원자료 시간 그래프에 공통 적용한다. 사용자가 고른 X/Y 두 변수의
관계를 보는 그래프는 각각의 독립 축을 유지한다.

### 화면 문구

활동 정의의 선택 항목 `channelNames`는 채널 ID별 표시 이름이다. 새 실험을 구성할 때
센서 채널의 이름만 바꾸며 ID·단위·범위·물리량·수집 방식은 유지한다. 준비·측정·분석·출력은
그 실험의 같은 이름을 사용한다. 기존 저장 자료의 채널 이름과 원자료는 다시 쓰지 않는다.
활동의 탐구 질문과 소개는 `uiCopy.preview.question`·`description`에 두며 비어 있는 공통 미리보기에는 표시하지 않는다.
센서 선택 카드의 제목·사용 센서·설명은 `uiCopy.home.sensorTitle`·`sensorEquipment`·`sensorDescription`에 둔다.
제목·설명이 비어 있으면 센서 이름·측정 항목 목록을 사용한다. 활동 카드는 `activityTitle`·`activityEyebrow`·`activityDescription`을 사용하며 제목이 비면 활동 이름을 쓴다.
활동의 `curriculum`·`curriculumDetail`은 검증한 교육과정 연결을 표시한다. 사용 센서는 해당 센서의 문구를 상속하고, 관련 활동 목록은 등록된 `sensorIds`에서 파생한다.
카드의 짧은 제목은 표시용으로만 쓰고 저장된 센서 정의의 이름을 바꾸지 않는다.

게이뤼삭의 교육과정 연결은 경기도교육청 [2022 개정 교육과정 고등학교 과목 선택 안내자료](https://www.goe.go.kr/resource/old/BBSMSTR_000000030136/BBS_202404250409254370.pdf) 인쇄면 112의 ‘물질과 에너지 → 물질의 세 가지 상태 → 이상 기체 방정식’을 근거로 한다. 이 활동은 일정한 부피·기체량에서 온도–압력 관계를 탐구하며, 성취기준 전체의 충족을 뜻하지 않는다.

`lab.html`과 `src/ui/`의 화면 모듈은 모든 실험실이 함께 사용하는 템플릿이다.
상단 메뉴·파일·미리보기·준비·측정·분석·해석·저장 목록·확인 창의 기본 문구는
[`ui-copy.js`](ui-copy.js)의 `labDefaults`에 있다. 문구를 바꿀 때 HTML이나 센서별
화면을 복제하지 않는다. 실험실별 차이만 센서 또는 활동 `index.js`의 `uiCopy`에 지정한다.

```js
export default {
  definition, decode, mockLine, guide,
  uiCopy: {
    preview: { eyebrow: '실험 안내' },
    measurement: { start: '측정값 기록' },
    guideSteps: { equipmentTitle: '실험 도구를 준비해요' },
  },
};
```

적용 순서는 **공통 기본값 → 센서 지정값 → 활동 지정값**이다. 항목을 생략하거나
문자열이 아닌 값을 주면 앞 단계의 값을 유지한다. 빈 문자열은 명시적인 빈 문구다.
등록된 ID·버전으로만 읽으며 저장 파일·수업 설정이 UI 문구를 주입할 수 없다.
홈은 공통 문구, 미리보기는 탐색 대상, 준비·측정은 현재 실험, 저장 자료의 분석은
그 자료의 센서·활동 문구를 사용한다. 다른 실험실로 전환하면 기본값부터 다시 조립한다.

`guideSteps`는 공통 준비 단계의 제목·설명·행동 문구만 바꾼다. 단계 ID, 수신 조건,
보정 절차, 기록·저장 규칙은 바꾸지 않는다. 센서 전용 그림·보정 안내와 활동의
질문·분석 제안은 기존 `guide`, `content`, `definition`에 둔다.

공통 문구를 추가할 때 기본값과 해당 화면의 `data-copy="영역.항목"`을 연결한다.
입력 안내와 접근성 이름은 `data-copy-placeholder`, `data-copy-aria-label`,
`data-copy-title`을 사용한다. 아이콘·입력창이 있는 요소는 글자 부분에만 연결한다.
상태·개수에 따라 달라지는 문구는 화면 모듈에서 같은 기본값과 `{count}`, `{name}`
자리표시자를 사용한다. 문구 변경은 입력 초안·원자료·분석 내용을 변경하지 않는다.

센서 안내처럼 전용 정의에서 이름을 결정하는 요소에는 공통 `data-copy`를 중복 연결하지 않는다. 상태에 따라 문구를 조립하는 하위 View는 현재 화면의 `getCopy()`를 받아 사용하며, 화면 갱신 때 고정된 기본 문장을 다시 쓰지 않는다. 문구 검사는 임의의 개별 문구를 주입하여 첫 표시·재렌더·다른 실험 전환에서 유지와 초기화를 확인한다.

## 준비 안내의 고정 슬롯

보드의 공통 동작·명령·LED 표시는 [센서 프로그램 공통 동작 규약](../../docs/sensor-program-contract.md)을 따른다. 사용자 안내의 명칭은 ‘센서 프로그램’으로 통일하며, USB·무선은 설치 방법으로 구분한다.

공통 순서는 준비물 → **sensor.beforeProgram** → USB·프로그램 → 연결 →
**sensor.afterConnect** → 새 값 수신 → **activity.afterReception**이다.

- 외부 배선은 `beforeProgram`, 자기장 보정은 `afterConnect`, 배터리·용기 배치는
  `afterReception`에 둔다. 일반 내장 센서는 추가 슬롯 없이 공통 순서를 사용한다.
- 단계에는 `id`, `kind`, `scope`, `required`, `group`, `groupLabel`, `title`,
  `description`을 지정한다. 버튼 문구는 `action`으로 정한다.
- 지원 종류는 사용자 확인 `manual`, 보정 `calibration`, 배터리 수신 `battery`다.
  보정·배터리는 기존 관측 처리와 연결되므로 각각 `calibration`, `battery` ID를 쓴다.
  공통 단계 ID(`equipment`, `usb`, `program`, `connection`, `reception`)와
  UI 예약 ID(`summary`, `quick`)를 새 단계에 사용하지 않는다.
- `quickConfirm: true`는 준비된 장치 요약에 넣을 **센서의 수동 확인**에만 지정한다.
  연결·수신·보정·배터리 확인을 이 요약으로 대신할 수 없다.
- 배선은 `guide.wiring`, 배선표 제목·단자 도움말은 `guide.wiringTable`에 둔다.
  `beforeProgram` 단계와 배선 항목의 ID를 맞추면 현재 연결을 표에서 강조한다.
  3D가 없는 센서도 같은 배선표·단계 확인을 사용한다.
  BMP280·DS18B20의 공통 3D URL·제목·보기 선택 항목과 기본값은 `guide.viewer`에 있다.
  센서별 `wiring.js`가 설명과 연결 구성을 소유하고, 공통 뷰어는 등록된 구성만 표시한다.
  단자·묶음 케이블·젠더·확장 보드 교체 계약은 [공통 장치 자산](../../public/assets/devices/README.md#외장-센서-연결-구성)을 따른다.
  내장 센서는 이 자원을 요청하지 않는다. 보기 선택은 준비 완료나 실제 연결을 뜻하지 않는다.

활동은 같은 방식으로 `activities/<id>/index.js`를 등록한다. 일반 활동 주소는
`definition.sensorIds[0]`을 기본 센서로 사용한다. 다른 센서를 기본으로 삼으려면
호환 센서 순서를 명시적으로 정한다. 활동의 질문·사건·계산 제안은 정의에, 실행 규칙은
policy에 둔다.

`tests/unit/registry.test.mjs`는 검사용 추가 내장 센서와 활동으로 이 확장 경로를
검사한다. 검사용 센서는 운영 목록이나 펌웨어 허용 목록에 등록하지 않는다.
작업 중에는 변경한 모듈과 영향을 받는 호출 경로의 검사만 실행한다.
전체 검사는 커밋 직전에만 실행하며, [검사 운영 원칙](../../AGENTS.md)을 따른다.

온도·밝기·가속도는 이 절차로 등록된 내장 센서 예시다. 공통 숫자 해석은
`sensors/shared/decimal-codec.js`를 사용하고, 단위·열 순서·범위·모의 값은 각 모듈에 둔다.
모의 장치의 송신 간격은 파일에 저장된 설정이 아닌 펌웨어 허용 목록의 명목 간격을 따른다.

## 장치와 주고받는 센서 전용 준비

MLX90393처럼 기록 전에만 설정을 변경하는 센서는 같은 preparation에 `createSettingsView`와 `configureContext`를 제공한다. 공통 준비 미리보기와 설정 창이 같은 뷰를 사용하며 제어기가 첫 기록 이후 변경을 차단한다. 확인된 설정은 `context.setup.sensorSettings`에 저장한다. 세션은 전달받은 설정을 검증하고 재연결 시 적용하며 `processReading`에서 요청 토큰을 확인해 수신 허용 여부를 판단한다. 단위 변환은 codec이 소유한다. 설정 변경 시 Transport는 이전 수신 확인을 초기화한다. 상세 계약은 [MLX90393 설계](../../docs/mlx90393-design.md)를 따른다.

자기장처럼 수치 수신 전에 장치 응답과 사용자 선택이 필요한 센서는 `index.js`에
선택적 `preparation`을 등록한다. 계약은 `src/device/preparation-types.js`에 있다.

- `createSession`: 연결마다 생성한다. 명령·상태 순서·응답 제한시간을 소유하며
  수신 허용 여부를 반환한다. 공통 Transport는 연결 수명과 실제 송수신을 담당한다.
- `createView`: 공통 가이드의 준비 패널에 센서 전용 그림·문구·행동을 표시한다.
  현재 상태에 맞는 단계와 수치 표시 여부를 제공한다. 공통 가이드에 센서 ID 분기를 넣지 않는다.
- `createMock`: 같은 프로토콜의 모의 응답을 만든다. 연결 해제 때 대기 작업을 정리한다.

codec의 `device-status`는 센서 세션으로만 전달하고 측정값·연속 수신 횟수·원자료에
포함하지 않는다. `allowReadings` 뒤에도 기존 연속 수신 검사를 통과해야 기록할 수 있다.
등록되지 않은 저장 파일은 이 실행 확장을 주입할 수 없다. 온도·조도·가속도·BMP280는
이 확장 없이 기존 준비와 수신 경로를 사용한다.
